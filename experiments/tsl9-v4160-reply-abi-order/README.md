# 頁面回覆：明確的來源 ABI 排序

[English](readme.en.md)

這個範圍有限的後端，會在新編譯的獨立
`tsl9_ota_page_reply_9b8e` 函式中恢復兩段指令順序。輸入必須是
124 bytes、50 條指令的 RV32 RVC soft-float ET_REL，只有一個已配置函式，
以及一筆指向 `__tsl9v4160_call_8a56` 的實際 `R_RISCV_JAL`。
它不產生 opcode，也不載入韌體。

第一段是函式偏移 `[0x02,0x16)`，含六筆編譯器堆疊保存、`LUI S2`
及配置器槽位的 `LW A5`；第二段是 `[0x58,0x60)`，含釋放槽位
`LW T1` 及 RA、S0 還原。策略以解碼後的暫存器與運算元指定順序，
輸出每一個指令字都來自同一段實際新編譯輸入。生成不讀取原始 BIN，
不內嵌原始指令模板，不補齊，也沒有後備資料來源。

這是明確加入的來源 ABI 契約，LLVM 本身沒有產生最終順序。把駐留服務
指標載入移到堆疊保存之間，可能改變發生錯誤或非同步事件時的前綴行為，
記憶體別名尤其需要注意。因此這個後端不宣稱任意環境下編譯輸入與輸出
語意等價；它驗證特定來源指令串，並記錄額外的處理階段。

## 使用方式

需要 Python 3.10 以上。三個產物路徑必須解析至指定專案內，輸出與收據
只能新建。專案內亦須存在固定雜湊的 ELF 解析器及獨立原始指令解碼器。

```sh
python experiments/tsl9-v4160-reply-abi-order/order.py \
  --project-root . --input path/to/fresh/page_reply.o \
  --output path/to/new/reply-ordered.o \
  --receipt path/to/new/order-receipt.json

python experiments/tsl9-v4160-reply-abi-order/order.py \
  --project-root . --replay --receipt path/to/new/order-receipt.json
```

獨立原生編譯物的函式確實是 GLOBAL FUNC、大小 124。原始完整映像的
公開入口則為 NOTYPE、大小 0，另有一個供外部引用的區域入口。這個
獨立處理器不自行建立或修改完整映像的入口角色，也不接受完整映像物件。

## 驗證範圍

處理器核對指令邊界、兩段精確的編譯器順序清單、來源運算元、固定呼叫、
分支及返回位置、區段所有權與屬性、符號及重定位錨點，以及檔案儲存別名。
重複套用及非預期輸入會被拒絕。兩段以外的每個位元組保持不變，包含中繼
資料、符號、重定位及尚待解析的 TX JAL。輸出再次獨立解碼並核對全部
50 項來源操作；只有那筆實際 JAL 重定位會依宣告目的地正規化。

唯讀重播重新計算完整轉換與收據，再比較實際輸入、輸出及保留的中繼資料。
收據記錄處理器、策略、ELF 解析器及原始解碼器的雜湊。處理器本身不能
證明輸入物件的 C/C++ 編譯來源，這項證據必須由元件編譯驗證器另外提供。

過程不執行或模擬 CPU 狀態及目標指令。未知駐留服務對 SP、S 暫存器的
保存方式、指標表有效性、實體硬體、完整映像整合及 BLE OTA 相容性，
仍是分開處理的必要條件。目前不宣稱可燒錄。
