# 32-byte 訊息的入列標頭從何而來？

對象為 V1.31 候選 resident（SHA-256 133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22），採條件 Xwchc 解讀。從 0x4e2ee 同一合成記憶體追到 0x4354a 入口或返回 0x4dffe，沒有拿新 fixture 代替訊息標頭。

1. 0x20000236 收到長度 32，0x2000026e 以大小 40、標籤 0xf020 呼叫 0x20000040。此內層 heap 的返回 P 為注入結果。
2. P 非空時，0x20000274 寫 word 0 到 P，0x20000278 寫 halfword 32 到 P+4，0x2000027a 寫 byte 255 到 P+6。返回 M=P+8。P+7 不屬於這三次寫入；兩個非零初始圖樣在入列後仍保留。
3. 呼叫者填寫 M 開始的訊息並要求複製 24 bytes 到 M+8；在來源與各物件分離、複製成功的模型下，0x4325a 讀 M−8 仍為 0，0x43260 讀 M−2 仍為 255。ID=7、count=8 時通過，M−2 改為 7；空表更新表頭，非空表更新先前尾節點，接著抵達 0x4354a(7,0x8000)。尚未執行事件派送。
4. P 為零不寫上述標頭，返回 0x4dffe，未經入列檢查且表頭不變。

一般與 -O 均通過：`8 allocator-to-append paths, 4 null returns; size 40/tag f020, header (0,32,ff), ID 7`。兩個成功區塊位置、兩種表頭與兩種原有圖樣；空指標分支亦跑兩種表頭及圖樣。未證下層 heap 在實際裝置一定配置成功，亦非自開機連續執行。
