# 何時能在旗標判斷前把共用 ID 從 255 改掉？

接續[固定選項 8 的旗標](v4160-bit14-option8-gate.zh-TW.md)。以下是以原 APP 和 V1.31 參考 ROM 推導的**有條件登記序列**，不是 RAM 擷取值。與其直接假設登記成功，先從 APP 算容量，再數兩次角色初始化之間的明確登記。

* APP `0x19a54` 建立 `0x1000`，`0x19a66` 減 449，`0x19a70` 以半字將 `0x0e3f` 寫至 `sp+36`。配置起於 `sp+16`，所以 `cfg[21]=14`。若 64-byte 複製到 `0x200031ec` 後該 byte 保持，則 `0x20003201` 為 14，低兩位為 2、高六位為 3。兩個角色的遮罩檢查都能通過；`0x43b8c..0x43bb4` 的容量為 `14+3*(2+3)=29`。
* 若初始三筆內部登記和 APP `0x19b2e` 如[先前驗證的順序](v4160-first-app-registration-order.zh-TW.md)成功，計數為 4。main 在 `0x8eb0` 先呼叫 `0x907a`，該函式 `0x90a2` 經 `[0x40080]` 以 `0x901a` 為 handler 再登記一次，返回值低 byte 另存 `gp+166`。名義上得到 ID 4，計數為 5。
* 第一角色槽 `[0x401a0]` 的候選 `0x6dd16` 直接呼叫 `0x43c4e` 六次：`0x6dd26/36/46/56/66/76`。若所有中間呼叫正常返回且不另改計數、容量或共用 ID，這六次用去 ID 5..10。尾跳 `0x6d572` 後，若共用 ID 仍是初始化值 255，`0x6d5b2` 登記 `0x6d26c`，`0x6d5b6` 寫回 **ID 11** 至 `0x200035f5`。
* 下一個槽 `[0x401ac]` 的候選 `0x6dd86` 在 `0x6dda0` 對 `(shared_id-1)&255 <= 253` 跳過另一組初始化；對 ID 11 成立。尾跳 `0x6ae7c` 後，名義上以 **ID 12** 登記另一個 handler（寫到 `0x20002fb0`，不是共用 ID）。隨後 `0x6ae5a` 仍讀到 11 而非 255，於是把旗標 `0x200035ab` 設為 1。後續固定選項 8 的讀取若仍見 1，便略過目的 ID 設定。

**容量界限。** 保持容量 29 與相同控制路徑，若在六次直接登記前已有 `n` 筆，且只有這六次可改計數，第一個角色登記成功需要 `n+6<29`（`n≤22`）。要讓下一個也成功需 `n≤21`。這區分了「共享 ID 已不是 255」與「下一個角色也成功」；不是兩者必然同時成立。未證所有中間子函式都不額外登記、動態寫入或非同步干擾；缺實際 ROM 身分證據。可優先查六個直接呼叫間各段有無再呼叫登記函式，而非把 11、12 視為固定韌體常數。
