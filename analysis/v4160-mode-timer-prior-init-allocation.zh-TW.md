# 初始化中先有配置，但不是從小額游標起找

接續[剛初始化時的 16-byte 模型](v4160-mode-timer-first-node.zh-TW.md)。要區分「整個配置區第一次被使用」與「小額起始標頭仍可用」。

原 APP 的 `0x19ae2..0x19aec` 讀取表項 `0x400a4`，以 `sp+16` 設定結構呼叫；非零返回時不走 `0x19af2` 的繼續路徑。V1.31 參考表項是 `0x43c7e`。沿該候選正常初始化路徑，`0x43d4c` 呼叫 `0x43b3e`；`0x43b88` 先呼叫配置區初始化 `0x43104`，返回後的直線指令計算大小，`0x43bbe/0x43bc2` 再呼叫 `0x20000040`，其結果在 `0x43bc6` 存入 `0x2000322c`，`0x43bca` 才檢查是否為零。不能只因提交了請求就斷言配置成功。

令 `c` 為 `0x20003201` 的實際讀值；請求大小是 `576 + 6 * ((14 + 3*((c>>2) + (c&3))) & 255)`，標記為 1。窮舉 256 個 c 得 660..1848 bytes（端點，不表示區間內每個值都出現）。若 APP 名義設定 `c=14` 保持，請求 750，向上對齊至 752。所有情況均超過小額門檻 52，所以這個請求從 `0x20003190` 的大額游標開始，而非從 `0x20003194` 的小額游標開始。

**結論：**在經此初始化後才進入計時器的路徑，16-byte 計時器不是第一個配置請求；但這一筆較早請求也不是小額標頭已被使用的證據。因此既不能直接指定計時器取得 `0x200043b4`，也不能僅憑這一筆排除它。下一步只檢查成功路徑上 `0x43c00/0x43c04` 的兩個初始化呼叫是否使用小額游標。不假設所有執行路徑、回呼或真機時序相同。

離線核對原 APP 與參考檔雜湊、表項、候選呼叫及指令視窗；Python `-IOB` 檢查初始化與配置呼叫目標、大小計算及全部 256 種游標選擇。未連接設備或修改韌體。
