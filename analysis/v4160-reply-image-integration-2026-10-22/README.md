# 十二個可讀函式的完整離線映像

[English](readme.en.md)

本輪把 `0x9B8E..0x9C0A` 的 C/C++ 頁面回覆函式納入完整映像。
可讀來源現在涵蓋十二個函式、650 bytes；其餘 679 個承載區段保持原內容。
輸出長度 76,800 bytes，與官方 ID2966 V4.1.60 原始映像一致：
`0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。
這仍是部分來源重建，不是完整原始碼還原。

## 證據與重做方式

| 範圍 | 入口 | 限制 |
| --- | --- | --- |
| 實際舊物件、來源與新入口的整合計畫 | [計畫](image-plan/README.md) | 預設只查封存與來源，不把計畫當完成的建置 |
| 新編譯、兩次排序、完整連結與輸出 | [實作](implementation/README.md) | ROM 僅數值地址見證，沒有提供實作 |
| 獨立來源、依賴與生成順序檢查 | [來源審查](source-review/README.md) | 紀錄反例與實際產物驗證分開 |
| 區段、符號、重定位、LOAD 與 BIN | [ABI 審查](ABI-review/README.md) | 實際 ELF／BIN 證據不證明原硬體 |

新流程編譯 34 個原始承載單元及 9 個可讀單元，另生成 9 份 LLVM IR。
61 個命令包含 59 個 LLVM 操作及兩次 Python ABI 處理：先重排獨立回覆
函式的既有指令字，再部分連結，最後恢復 IRQ／quarter 的保存順序。
不增加 opcode 或填補、不以原始 BIN 回填，也不宣稱編譯器單獨輸出最後次序。

全部 43 個編譯單元使用完整 `-MD`，實際閉合 74 份專案輸入、14 份生成
輸入與一份 Clang 資源標頭。這修正了依賴證據的範圍：舊 `-MMD` 沒列出
系統標頭，並不代表編譯器沒有使用它們。

完整配置仍為 691 個區段，含 8,257 筆保留的外部重定位與 12 筆來源 JAL，
合計 8,269；53 個相對綁定及 21 筆來向入口都維持精確角色。原始回覆
公開入口保持 NOTYPE／size 0，區域入口保留，新增 C 函式另為 FUNC／124。
`0x9DF4` 仍是更新 RA 的 `C.JAL`，原始私有分支按精確運算元及目的地閉合。

生成物中的 `.llvm_addrsig` 增量有獨立的原始前綴、新編譯單元位元組及
符號來源檢查；它是排除於最終載入映像的中繼資料，不能因此忽略任意增量。
15 個 LOAD 的檔案／記憶體範圍、權限與全部輸出位元組皆須核對。

## 尚未完成的完整目標

嚴格連結仍拒絕未知 ROM 實作，數值 `0x40000` 只供地址見證。原硬體、
晶片與板子、已安裝 ROM／BOOT、記憶體與中斷、BLE OTA 接受與復原仍須
實際證據。使用者曾成功更新的官方檔案身分尚未與本映像精確核對。

**目前未驗證可燒錄，完整目標保持進行中。** 未執行或模擬 RV32，未操作
BLE／CAN／UART／Flash 硬體。離線更新前的頁面範圍與版本適用性檢查仍是
候選提案，沒有把它宣稱為已加入的裝置功能。

後續優先追查完整 OTA 處理器、TX 封裝及其外部服務，保留每個版本與
Runtime／BOOT 方向的證據邊界。Windows 的實際編譯證據與 shell、Linux、
macOS、CI 或實體硬體證據分開記錄。
