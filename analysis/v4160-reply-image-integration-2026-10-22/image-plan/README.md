# 十二函式完整映像整合計畫

[English](readme.en.md)

這份計畫從實際十一函式部分連結物件及已封存的 C/C++ 頁面回覆元件，
整理第十二個可讀函式的完整映像邊界。它不是完成的映像，也不證明硬體
或 OTA 相容性。先前所有封存保持原樣。

`prepare-plan.py` 實際重播先前完整物件的區段、符號及重定位檢查，並重播
新頁面回覆 C、C++ 的來源、編譯及固定地址產物；兩語言全部 124 bytes
與原始函式一致。然後核對其餘 679 個承載區段、8,257 筆外部重定位、
21 筆來向入口及既有 53 個區段相對綁定。這些是實際讀取的既有證據；
完整新建置的數量仍須另外驗證。

新函式的三份原生 C／標頭納入來源清單。實際 Clang 預處理也確認 C、
C++ 都讀取一份額外資源標頭 `include/stdint.h`，其位置與雜湊記錄在
清單。完整建置須以完整依賴紀錄重新測量所有單元，不能因舊 `-MMD`
輸出未列系統標頭，就宣稱沒有讀取。

## 入口與生成鏈

原始公開入口為 GLOBAL NOTYPE／size 0，區域入口是 LOCAL／size 0。
它們保留在原始區段的零位元組起點；真實新 C 函式另有 FUNC／size 124。
連結腳本把新函式放到同一區段，不建立 ABS 入口別名、不增加邊界位元組。
來向 `0x9DF4:69 3b` 是 `C.JAL`，會寫入 `RA=0x9DF6`，不能只根據
R_RISCV_RVC_JUMP 的名稱推斷無連結跳轉。

預定生成順序是：新編譯獨立頁面回覆、明確重排兩段既有指令、與其他
新編譯單元部分連結，最後恢復 IRQ／quarter 的保存順序。兩個排序步驟
都有獨立來源與收據，不宣稱 Clang 單獨輸出最終次序。原始 BIN 只作
比較證據，不是程式碼生成、填補或後備輸入。

`typed_provider_object_sha256` 表示部分連結前實際使用的指令串；對頁面
回覆而言，它已經過明確排序。`raw_compiler_native_object_sha256` 才是該
函式最初的編譯器輸出，兩者必須區分。

## 檢查

```sh
python analysis/v4160-reply-image-integration-2026-10-22/image-plan/check-plan.py \
  --project-root .
```

預設只核對封存與目前來源／標頭，不讀取歷史物件或 BIN，也不重新執行
計畫建立程序。`verification.json` 保存實際建立計畫時的檢查與三個有界
Clang 依賴查詢；封存中繼資料不能取代新完整映像的實際產物驗證。

尚須核對完整新映像的每個區段、保留內容、符號、重定位、固定位置、
LOAD 檔案與記憶體範圍、權限及輸出內容。未知 ROM、實體硬體、啟動與
更新條件仍獨立待證。目前不宣稱可燒錄。
