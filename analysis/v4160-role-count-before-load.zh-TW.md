# 讀取配置計數前，三個清零呼叫是否會改掉它？

接續[啟動清零證據](v4160-startup-role-count-clear.zh-TW.md)。只看 V1.31 候選 `0x4da70` 與它直接呼叫的 `0x4edd2`；不假定其他啟動呼叫保留 RAM。三組 AUIPC/JALR 都解出 `0x2000039c`。若 RAM 程式與參考複製內容一致，其迴圈先增加游標，再向 `游標-1` 寫 byte，因此最後一筆是 `起點+長度-1`。它另存取 `0x4002420c` 的 word，該位址也不是目標計數。未建模間接硬體副作用。

| 呼叫點（執行先後） | 目的與界限 |
|---|---|
| `0x4ee20` | 目的為配置返回的指標，長度為重新讀取的總數乘 60；`0x4ee1c` 只把指標本身存到 `[0x20003354,0x20003358)`。知道指標存放處，不等於知道它指向哪裡。 |
| `0x4ee4e` | 尾呼叫；固定清零 `[0x20003358,0x20003388)`，從計數位址後 8 bytes 才開始。 |
| `0x4daea` | helper 返回後固定清零 `[0x20003320,0x20003350)`，最後寫 `0x2000334f`；隨後 `0x4daf6` 才讀 `0x20003350`。 |

前兩個呼叫屬非零總數路徑，不是每次都執行。另依既有 Xwchc 解碼，`0x4edec`、`0x4edf4` 的兩個計數欄位是 `0x200033b5`、`0x200033b4`，並非這個 byte。此處排除兩次固定填寫及存指標的直接覆寫；尚未排除配置器、動態區塊的填寫與逐筆初始化、堆疊或更早呼叫。不能宣稱計數在讀取時為零。

驗證：`python analysis/check_v131_role_fill_destinations.py <V1.31-reference-carrier>`；核對 carrier SHA-256、四段指令、三個呼叫目標和固定位址；一般與 `-O` 皆通過。這是離線指令與範圍檢查，不是裝置觀測。
