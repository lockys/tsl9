# 描述元設定函式 `0x640b8`：直接呼叫編碼盤點

問題是能否從一個明確的呼叫點向上追到傳入的 D。[上一階段](v4160-type3-descriptor-setter.zh-TW.md)已確認 `0x401e8` 存的是函式位址，不是描述元。這次未找到可用於回溯參數的直接呼叫點。

在 SHA-256 固定的 V1.31 carrier 上，[檢查程式](check_v131_descriptor_edges.py)每隔 2 bytes 取一個視窗，解碼 RV32 JAL（所有 rd）、標準 C.J／C.JAL，以及相鄰且暫存器相接的 AUIPC + 32-bit JALR。用算出的目標位址對比 `0x640b8`，不以反組譯器的符號名稱做搜尋。結果：

| 位址解釋 | 掃描 bytes | 符合編碼 |
|---|---:|---:|
| 原參考 carrier，自 `0x40000` | 191078 | 0 |
| 假設 seed 和第一段拷貝成功，自 `0x20000000` | 11892 | 0 |

同一解碼器能辨識 4 個已知轉移（含一個負位移跳轉），並排除各自偏移 2 bytes 的錯目標；一般及 `-O` 模式輸出相同。重跑：`python analysis/check_v131_descriptor_edges.py <V1.31-carrier>`。

這不是「沒有呼叫者」：未涵蓋表間接呼叫、載入與跳轉不相鄰、其他指令形式、未映射記憶體或不同 ROM。取樣包括可能是資料的視窗，不證任何控制流可達。現有證據能限定 D 的使用方式，仍不能給 D 或其兩個目的指標賦固定地址。後續應查 API 表或 SDK 對此表項的命名及參數宣告，而非把無命中當成 D 永遠為零。
