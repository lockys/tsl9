# `0x6645c`：兩條路徑對 RAM 計數的影響

接續[五個子呼叫](v4160-role-641b0-five-calls.zh-TW.md)。範圍是 V1.31 參考 carrier，壓縮 byte load/store 按 Xwchc 解碼，不是實機 ROM。問題是兩條路徑的直接 store 是否觸及 `0x20003350`。

| `0x664d0` 比較 | 分支獨有的非堆疊 RAM 寫入 |
|---|---|
| `[0x20003588] == 0x12345678` | `0x67190` 將同一個 word 清零，`0x67194` 跳至 `0x665b0`，不是直接返回。 |
| 不等 | 依序寫六個 byte：`0x20002fa6, 0x20002fa7, 0x20003595, 0x2000358c, 0x20003594, 0x20003584`。每對的值分別為外設 `+144` word 的低 6 位及 `+148` word 的 bits 10..16。第二個位址經 `12(sp)` 保存再載入。 |

不等路徑的三組 AUIPC/JALR 均到 `0x20002df2`。按參考映射，此 helper 寫 `6000` 至 `[[0x2000353c]+100]`；之後輪詢，未證必返回。完整六筆寫入以三次正常返回為條件。

共同尾段 `0x665b0..0x6718e` 有 109 個以 `a5` 為基址的 word-store 指令位置，以及一個 `8(sp)` 的暫存寫入。`0x665bc` 從 `[0x20003590]` 載入基址，偏移為 `4,40,44,56` 及 `160..208`（每 4 bytes）。當該基址保持 `0x40025000`，且 helper 的另一基址保持 `0x40024200` 時，這些是外設位址，不是計數。入口另有 80-byte stack frame；結論假設正常獨立 stack、指標未被改寫，不推論外設副作用、中斷或整段初始化的最終計數。

重現：`python analysis/check_v131_6645c_stores.py <reference-carrier>`。檢查固定 SHA、三個 call target、選定分支 store 編碼與共同尾段 store 分布；不是 CPU 模擬或硬體測試。
