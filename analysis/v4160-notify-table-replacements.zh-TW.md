# 預設通知表何時可能改變？

[三張預設表](v4160-notify-table-loads.zh-TW.md)均不派發 111、112、113，但這不是執行期間的不變條件。原 APP 有兩段帶條件的設定更新程式：`0x14af4` 起的分支可更新第一表；`0x14bc6` 起的分支選擇另兩表之一。兩者都有長度及末端標記檢查。在通過檢查的路徑上，APP 從表槽讀取當下的指標，要求 `[0x4004c]` 複製 256 bytes，並在正常返回後直接呼叫對應的儲存包裝。若複製服務按參數完成，寫入範圍涵蓋整張表，包括派發器比對的鍵及雙表的啟用位；不代表寫入的內容一定不同、一定命中或已在裝置上發生。

|即時目的指標槽|複製呼叫|隨後的儲存包裝|包裝讀取的固定 RAM 來源|
|---|---|---|---|
|gp+96|0x14b1a|0x12e54|0x2000c494|
|gp+100|0x14c20|0x12f48|0x2000c594|
|gp+104|0x14bf4|0x13052|0x2000c694|

兩次複製的位址來源不同：更新以即時指標為目的，包裝則以 PC 相對指令取固定來源，將快照複製到棧後交給 `0x9c0a`。固定來源等於 reset 初始化指標；不能據此推定指標後來必然不變，也不能把呼叫包裝視為持久化成功。另在 `0x13682`、`0x13776` 讀出的表指標被存到描述子的 +4，不是這兩條路徑直接改寫表項的證據。

`python analysis/check_v4160_notify_replacements.py <decoded-bin>` 固定原 BIN SHA，檢查三組槽偏移、複製呼叫、後繼 JAL 目標和固定快照來源與 reset word 的關係。這是靜態佐證，不是全域寫入者清單、裝置資料或呼叫可達性證明。
