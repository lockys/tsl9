# 在旗標讀取前，`0x6c0f0` 會改變它嗎？

接續[固定選項 8 的分支](v4160-bit14-option8-gate.zh-TW.md)。原 APP `0x1237a..0x12382` 以 PC 相對運算給 `a1=0x1a668`，並間接呼叫。若槽 `0x401b0` 維持 V1.31 參考綁定，非零 `a1` 讓 `0x6ada0` 呼叫 `0x6c0f0`；不能把這次呼叫略去。

| 執行位置 | 來源 | 寫入目的（不含堆疊） |
|---|---|---|
| `0x6c102` | 進入 `0x6c0f0` 的 `a0`，即外層傳來的指標值；這裡不解參照 | `0x20002fe0`，4 bytes |
| `0x4653c` | `U8[0x20002fc2]` 的第一次取樣，零擴展後寫成半字 | `0x20003268 + 2*24 = 0x20003298`，2 bytes |
| `0x4cfca` | `0x6c10e` **再次**讀 `U8[0x20002fc2]`；由 `0x6c116` 尾跳過來 | `0x20002ee0`，1 byte |

`0x46506` 在此收到 `a0=24`、`a1=0..255`，所以不超過索引上限 65，不會碰到半字哨兵 65535，也不等於有額外子呼叫的索引 17、58、59。選中路徑直接寫表後返回。兩次取樣不必假設相等：改變值不會改變三個目的位址。壓縮 byte/halfword 指令依候選 Xwchc 解讀。

另有 5 筆 stack word save：相對 `0x6c0f0` 入口 SP 為 `-8,-4,-24,-20,-28`。若這些槽及外層 frame 與相關狀態分離、保存值正常還原、記憶體存取成功且無外部干擾，這個子呼叫不改 `0x200035ab`。返回後 `0x6adac` 可能將還原的 `a2` 寫到固定 `0x20002fb4`，也不涵蓋旗標，隨後 `0x6adb4` 才讀旗標。因此若呼叫前旗標是 1，在上述條件下仍會略過設定；這不證實呼叫前實際是 1，也不證實設備使用參考 ROM。

重現：對 SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22` 的 carrier，PC 減 `0x40000` 取偏移。兩次 LBU 原碼 `0c20`、`0820`；表寫入 `06a0`；其餘兩個 store 為 `23a0a7fe`、`2380a7ee`。核對三個 branch 目的地 `0x4654a/0x4655a/0x46530`，即可區分實際走的寫表分支與附近未執行的呼叫。
