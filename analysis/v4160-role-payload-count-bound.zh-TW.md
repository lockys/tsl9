# 動態配置的寫入是否會碰到 `0x20003350`？

接續[固定寫入範圍](v4160-role-count-before-load.zh-TW.md)與[名義配置區初始化](v4160-mode-timer-arena-init.zh-TW.md)。本次只檢查配置成功後的填寫與記錄初始化，不推論配置器內部所有副作用。

`0x4ee08` 請求 `60*((c&3)+(c>>2))` bytes。非零請求為 60..3960 bytes，皆選大額游標。候選配置器從該游標讀取標頭；不合適時 `0x2000010c` 改讀鏈上的下一個標頭，而非從固定位置返回。正常成功分支 `0x200000f4` 回傳 `P=H+8`。若沿用名義 APP 設定 `B=0x2000418c, L=0x7000`、遍歷的都是區內有效標頭，則可用整個區的寬鬆界限 `0x200043b4 <= P <= 0x2000b184`，不必猜測哪個區塊還空著。上界故意包含 sentinel 地址，不代表它能被配置。

- `0x4ee20` 清零從 P 起的 `60*n` bytes，n 是呼叫配置器後重新讀的 unsigned byte。即使只採用寬界 `0..255`，起點也高於 `0x20003350`，加法不繞回。
- `0x4ee28` 從指標欄位重新讀基址；若此讀值仍在上述範圍，逐筆初始化也不會碰到目標。第 i 筆直接寫入的 byte 偏移是 `60*i+{2,3,4,44,45,46,47}`（Xwchc 的 halfword store 加上兩個標準 store）。迴圈使用自己的 unsigned byte 次數，不必假定和清零長度的 n 相等。

**結論限於位址互斥**：在以上前提下，這兩組動態寫入可從計數來源排除。未證明現存鏈結、重新載入的指標、兩次長度與實際配置容量一致，亦不代表任意寫入都在有效物件內；配置失敗、其他呼叫、裝置 ROM 身分與讀取時的值均不在證明內。

`python analysis/check_v131_role_payload_bounds.py <V1.31-reference-carrier>` 核對映像身分與指令片段，檢查 256 個請求輸入、兩種獨立 byte 次數的上下界。普通與 `-O` 皆通過。
