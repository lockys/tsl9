# v4.1.60：事件記錄索引的直接寫入來源

接續[事件記錄資料方向](v4160-app-event-record-callback.zh-TW.md)，本輪區分 `gp+376` 的直接儲存、初始化和間接提供者。

| 位置 | 原指令觀察 |
| --- | --- |
| `0x1798a` → `0x179e4` | 無號 `a1 > 35` 跳到 `0x179fa`；未跳且 `a0 != 0` 時，`0x179e4` 將 `a1` 低位元組寫入索引。這條寫入路徑的值為 `0..35`。 |
| `0x177b2` | 條件式寫入零。`0x177a2` 是在間接呼叫返回後重新讀索引，不是沿用 `0x17780` 的值。 |
| `0x17bfa..0x17c0a` | 從 `[0x40048]` 取得間接目標，傳入 `(gp+376,0,3)`。只有目標確實提供所假設的清零語意時，才算索引的清零來源。 |
| APP 清零區間 | 若 `gp=0x20004000` 且原清零迴圈成功執行，索引位址 `0x20004178` 落在 `[0x20004080,0x2000c958)`。 |

用 SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 固定原 BIN，Python `-O` 掃描 38,399 個可取 4 bytes 的半字起點。標準 RV32 的 `gp` 基址直接 load/store，按寬度查與索引 byte 的交集，得到兩讀 (`0x17780`、`0x177a2`) 與兩寫 (`0x177b2`、`0x179e4`)。另掃到一個 `addi` 直接形成 `gp+376` (`0x17c06`)。用反組譯核對主要候選，並核對四個原始指令窗、清零區間與 38 個條件更新案例。

若只考慮已知兩個直接寫入及成功清零，索引維持 `0..35`，`0x17780` 取到的索引用於 `7*i`，最後一筆覆蓋記錄區偏移 `245..251`。這是局部推論，不是所有讀取時刻的保證：半字掃描不辨識全部指令邊界，不排除其他基址、衍生指標、其他映像或間接寫入，也不確認提供者的實作。下一步核對已知初始化呼叫的直接前驅，以及第一次讀取前可見的初始化順序。未改動原 BIN、正式來源或設備。
