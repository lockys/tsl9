# 設定 bit 4 處理後的同批寫回

在 `0x1431a` 重新載入設定指標 P=`U32[gp+84]`。`U8[P]` 與 `U8[s0+24]` 的低三位不同才呼叫 `0xfa3c`；它把 `U8[gp+276]` 複製到 `gp+277`，不是把比較的三個位元寫入設定。低三位相同只跳過這個小函式，兩路都到 `0x1432e`。

正常返回並保存相應暫存器時，APP 依序向槽 `0x4004c` 發出兩個 16-byte 複製請求：`s0+24 → P1`，然後 `s0+59 → P2+96`。P1、P2 分別在 `0x14336`、`0x14340` 讀取。隨後 `0x14352` 直接呼叫 `0x13138`；該包裝函式將固定地址 **0x2000c29c** 的 112 bytes 複製到棧，再請求 `0x9c0a(0x08077a00,sp)`。它不讀 P1/P2。因此若兩個指標都是固定來源，且複製正常、無干擾，兩段新值分別位於暫存區的 0..15 與 96..111；不能僅憑呼叫次序保證這件事，更不能據此證明 Flash 寫入成功。

返回後先呼叫 `0x9124(0x960e,0,100,0)`，再 `0x13dd4(0)`；`0x14370` 又取一次設定指標，讀 +4 的 bit 3，非零才呼叫 `0xe20c`。後續判斷不是根據剛複製時保存的值。核對程式對原 APP 機碼、六個直接呼叫與地址做靜態檢查，另以合成複製模型核對四種指標組合，非實機執行。
