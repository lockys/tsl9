# v4.1.60：resident 六位元組比較欄位的來源

接續[兩組結果的封裝與重試](v4160-resident-clock-wrapper-result-paths.zh-TW.md)。按原 APP、V1.30 原始 HEX 與兩版主段的 SHA-256 重新核對局部指令。APP `0x19abe..0x19ad2` 把 `[sp+8,sp+14)` 的六個 bytes 寫到設定結構 +24..29；本輪不推論其最初的來源或用途。

若 APP 設定已經由 [初始化函式](v4160-resident-config-clock-pointer.zh-TW.md) 正常複製，且沒有中途改寫，兩版 reader 之前的函式會把設定副本 +24..29 再複製到比較欄位 +232..237：

| 參考 | 函式入口／copy 呼叫 | 設定來源 | 比較欄位目的 | 上游尾跳 |
|---|---|---|---|---|
| V1.30 | `0x5370a`／`0x5372e` | `0x200030b4` | `0x20003350` | `0x5e60a` |
| V1.31 | `0x53868`／`0x5388c` | `0x20003204` | `0x200034a0` | `0x5e768` |

兩個 copy 呼叫都帶長度 6，目標為候選 RAM helper `0x20000332`。上游尾跳先對同一狀態基址 +200 寫零 byte、+204 寫零 word，再以 JAL x0 進入；未證該上游何時被實際呼叫。原始指令欄位與相對位址核對在 Python `-O` 下通過。

這證實一個比較欄位寫入來源，不是完整寫入者清單。已知本地會讀 +250..255 做比較，仍未找出兩組生成欄位 +244..255 的外部使用者；不根據六個 bytes 的長度或常數命名。原 BIN、正式來源未改，未執行韌體或連設備。下一步分別追 APP 填出這六個來源 bytes 的呼叫，以及生成欄位的其他讀者。
