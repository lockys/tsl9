# 要求廣播物件的兩條直接路徑來自事件處理函式

對象為 WCH V1.31 參考主區（SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`）。這裡追的是 12-byte 物件，不是參數 774 的 21-byte 緩衝區。

| 登記時傳給 `0x43c4e` 的 a0 | 直接呼叫登記服務 | 從該 handler 正常入口進入所查分支的必要條件 | 呼叫 `0x482f4` |
|---|---|---|---|
| `0x6a7e4` | `0x6ab74` | 傳入 a1 的 bit 15 清除、bit 0 設定；`U8[0x200035a8] != 0` | `0x6aa42` |
| `0x6d26c` | `0x6d5b2` | bit 15 與 bit 14 均清除、bit 0 設定；同一 RAM byte 非零；`0x4f128` 的無號回傳值不小於隨後讀取的 `U8[0x20003201] & 3` | `0x6d3b2` |

兩個登記點用 LUI/ADDI 構造 handler 位址，JAL 的目的都是登記服務，並非該 handler。兩個配置呼叫前則都重新讀 `U8[0x200035f5]` 作為 a0，a1 指向當時的 `sp+4`。針對這兩個 handler，參考主區半字對齊的 JAL、C.J/C.JAL、相鄰 AUIPC/JALR 掃描均未找到直接呼叫／跳轉到其入口。這不排除間接派送。

驗證：核對兩組 LUI/ADDI、登記及配置呼叫的直接目標，再枚舉 65536 個低半字；僅考慮 mask 條件時兩條路分別容許 16384、8192 個值。這不是實際事件數。要判斷 APP 首次設定 774 時指標是否仍為零，還缺初始化返回之前是否會間接派送這兩個 handler 的證據；僅登記或設定 pending bit 都不足以證明已執行。
