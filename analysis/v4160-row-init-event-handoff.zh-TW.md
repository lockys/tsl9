# 從三列初始化到連線事件回呼：中間隔著一次任務派發

原 APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。以下服務名稱對照參考 SDK，以 slot 基址及提供者維持名義綁定為條件。

- `0x1254e` 已將任務處理函式 `0x119c8` 交給 `[0x40080]` 註冊，回傳低位元組存於 `0x2000bfd4`。這不是連線事件回呼 `0x11544`。
- 三筆 handle 寫完後，`0x12606` 呼叫 `[0x400c4]`（GATT_InitClient）；`0x12618` 呼叫 `[0x400c8]`（GATT_RegisterForInd），參數是重新讀出的任務 ID；`0x12622` 又重新讀 ID，向 `[0x40050]`（tmos_set_event）提交遮罩 1。此處沒有測試發送結果，也沒有直接呼叫連線事件回呼。
- `0x1262c` 要求清零 `[0x2000bfc8,0x2000bfd4)` 共 12 bytes；`0x1263a` 註冊另一函式 `0x11442`，結果低 byte 寫 `0x2000bfc8`。這兩個具名目的區都不在三列 `[0x2000bfec,0x2000c010)` 內。這不是所有間接呼叫副作用的證明。
- 若任務 `0x119c8` 獲派發，當輪遮罩依序優先檢查 `0x8000,2,4,8,16,1`。只有最後的 1 被選中才在 `0x12382` 呼叫 `[0x401b0]`（GAPRole_CentralStartDevice），傳入回呼表 `0x1a674`；其 +4 為 `0x11544`。正常返回後清掉遮罩中的 1，不依啟動服務的回傳碼決定。傳遞回呼表不等於已收到 opcode 5，也未證服務返回前不會回呼。

核對：原 BIN 的 PC-relative 指標、表項、比較立即數及反組譯分支。對所有 65536 個低半字遮罩套用該優先序，1024 個選到啟動分支。結論限這條 APP 路徑：三列標記先於發送請求；實際收到第一個連線事件的時點、服務成功與派發前所有寫入仍未知。
