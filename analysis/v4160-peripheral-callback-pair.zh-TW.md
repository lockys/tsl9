# 周邊回呼表：連線狀態與參數更新，不是直接 PA 控制

輸入為原 APP，SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。`0x19de0` 的三個 RV32 word 是 `0x8b90, 0, 0x85c8`；按 2023-12 參考標頭 `gapRolesCBs_t` 的順序，分別為狀態變更、RSSI、連線參數更新。以下為 APP 指令的靜態行為，並非實機事件紀錄。

- `0x8b90`：狀態 4 且事件 byte +2 為 5 時，以事件 +10 的半字作為 handle，找 gp+150/+154 中第一個 `0xfffe`。都被占用則向 `[0x4017c]` 請求終止該連線；找到空位則保存 handle，以記錄的 task ID 發事件 4，再以 stack 上的半字 247 請求交換 MTU。之後重讀 handle 欄位決定是否要求啟用廣播，並非預設交換成功。
- 狀態 2 或 3 且事件 byte +2 為 6 時，用事件 +4 的 handle 找第一個相符欄位，改回 `0xfffe`，要求啟用廣播，重讀事件 handle 並呼叫 `0x13e0e(handle,0)`。這個 helper 使用另一個基址 `0x2000c794`；mode 0 若匹配，重設對應 handle 並清兩個 byte，若都不匹配則不寫。helper 內無其他呼叫。廣播 wrapper `0x8b6e` 是參數 `0x305`，不是 PA 描述元。
- `0x85c8`：先匹配 gp+150/+154 的 handle（先者優先），不匹配即返回。匹配時若 interval 在 **12..24（含）**、latency=0 且 timeout=200，亦直接返回；否則從該記錄重讀 task ID，尾跳 `[0x40058](id,4,4800)`。這是排程請求，不會在這裡同步執行事件 4，也不能推斷設備接受新參數。

檢查：按 16/32 位指令邊界掃描 `[0x8b90,0x8c82)`，除返回外，有三個間接呼叫及三個直接呼叫（兩次 `0x8b6e`，一次 `0x13e0e`）；`[0x85c8,0x8614)` 只有一個非返回間接尾跳。由 `0x85da` 和 `0x85e0` 解出門檻，窮舉 65536 個半字，僅 12..24 符合。兩回呼均未直接取用 PA 表項 `0x401e8`；此結論不排除外部服務內部行為，也不證明已安裝特定 ROM。
