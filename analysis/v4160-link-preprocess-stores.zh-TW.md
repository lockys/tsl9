# 連線前處理是否直接寫回事件？

V1.31 參考 carrier SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`。事件 M 的 opcode 5、status 0 路徑呼叫 `0x6c194(M[3], M+4, LE16(M+10), 8)`。以下區分函式本體的 store 與被呼叫者的寫入。

- `[0x6c194,0x6c2f6)` 共 354 bytes。以建立 128-byte frame 後的 SP 計，本體有 8 處直接 store：在 +104、108、112、116、120、124 各保存一個 word，並在 +4 寫零 word、+8 寫零半字。沒有以事件指標為基底的直接 store，也沒有直接寫保存回呼表指標的 `0x20002fb4`。下一條函式內的 `0x6c2fa` 不計入。若堆疊與事件及表槽分離，這八處不會改到它們。
- 不能因此判為唯讀。本體有 15 個 32-bit 呼叫位置，不是每條路徑都執行全部。第一個 `0x6c1b0` 呼叫 `0x6be3c`，傳入的 a1 仍是事件位址欄位 `M+4`，a2 則已換為本層 `SP+4`。回來後才以 `[0x20002fc1]` 的 byte 與返回值做無號比較。
- `M[3]` 為 0 或 1 時，`0x6be7c` **先把 `M+4` 傳入 `0x6b50c`**。若正常返回且結果小於當時的界限、輸出指標非零，`0x6be92..96` 再向 `0x20000332` 提出六位元組複製。保存暫存器有效時目的為外層 `SP+4`，來源才是 `M+4`。不能倒過來將它記成對事件欄位的寫入。類型 2、3 有不同分支；本節未涵蓋其所有子呼叫。

驗證：逐指令寬度掃描本體，重算 store 的位移與寬度、呼叫位置數及 PC-relative 複製目標。這只排除本體的直接寫入，未證實機 ROM、被呼叫者的全部副作用、或 APP 最終讀到的訊息與表未變。
