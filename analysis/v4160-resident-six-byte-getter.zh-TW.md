# v4.1.60：resident 六位元組讀取函式取的是基準值

接續[地址核對](v4160-resident-six-byte-address-audit.zh-TW.md)。在相同 SHA-256 固定的 V1.30／V1.31 參考映像中，沿狀態基址 `LUI/ADDI` 及輸出指標追查，找到一個有已確認直接呼叫者的六位元組讀取函式。它讀的是先前追到 APP 設定的基準欄位 `+232..237`，不是同一結構中另行產生的 `+244..255`。

| 參考版 | 呼叫者 `JAL x1` → 入口 | 狀態基址 | 輸入範圍（半開） |
|---|---|---|---|
| V1.30 | `0x670c6` → `0x67dae` | `0x20003268` | `[0x20003350,0x20003356)` |
| V1.31 | `0x67224` → `0x67f14` | `0x200033b8` | `[0x200034a0,0x200034a6)` |

兩個呼叫點均配置 32-byte frame、將 `a0` 設為 `sp+9`，並儲存 `ra`。函式把 `a5` 設為狀態基址、`a4=0`、`a3=6`；每輪執行 `lbu a1,232(a5)`，將 `a0+a4` 放入 `a2`，遞增計數，經 QingKe Xwchc byte store（`0c a2`，解作 `qk.c.sb a1,0(a2)`）後遞增 `a5`。第六輪完成後返回 0。通用 RISC-V 反組譯會將該壓縮 store 顯示為 `fsd`，本結論限定 Xwchc 解碼及成功讀寫。

Python `-O` 核對兩份樣本身分、相同 26-byte 迴圈、Xwchc store 欄位、兩個 JAL 目標和 stack 參數；各用兩組合成目的位址（包含 32-bit 環繞）驗證讀取範圍不碰 `+244..255`。這是靜態指令與範圍核對，不是硬體或完整 CPU 執行，也不表示生成欄位沒有其他間接讀者。未接設備或修改原 BIN／正式來源。
