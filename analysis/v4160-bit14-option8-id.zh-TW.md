# 固定選項 8 的收件 ID 也有登記來源

接續[四條設定路徑](v4160-bit14-setter-callers.zh-TW.md)，只追 `0x6adc8` 讀的 `0x20002fb0`。V1.31 參考映像的證據分三段：

1. **清零。** [候選 startup](rf-3538-init-coverage.zh-TW.md) 的 RAM helper 若已正確複製並執行，依 `0x40292..0x402ae` 對應的指令每次清一個 word。其 456 個目的位址中，從 0 起算第 46 個是 `0x20002fb0`。所以該 byte 的清零值是 0，不是固定 3，也不是另一個欄位 `0x200035f5` 的 255。
2. **角色登記會改寫它。** `0x6ae7c` 讀 `U8[0x20003201]`；高六個 bit 皆零時走返回 24 的路徑，不作這筆登記。否則 `0x6aeb2` 以 handler `0x6abc6` 呼叫 `0x43c4e`。若正常返回且 `s0` 保持，`0x6aeb6` 算出 `s0=0x20002fb0`，`0x6aeba` 將 `a0` 低 byte 寫到 `[s0]`。原碼 `08a0` 依候選 Xwchc 是 SB（quadrant 0、funct3 5、基底 x8、來源 x10、偏移 0），不是標準浮點解碼。**先寫後比**：`0x6aec0` 才測返回值是否為 255；即使登記回傳 255，該 byte 也已被寫入 255。
3. **APP 順序限制。** 原 BIN 的 `0x8eac` 呼叫 [APP 第一個登記函式](v4160-first-app-registration-order.zh-TW.md)，返回後再經 `0x907a` 和 `[s0+0x1a0]`，才在 `0x8eb8/0x8ebc` 讀 `[s0+0x1ac]` 並呼叫。若表基址仍為 `0x40000` 且使用參考綁定，此槽為 `0x6dd86`，其 `0x6de08` 尾跳 `0x6ae7c`。若 APP 已成功取得 ID 3、其後計數不重設或回捲，這次較晚的成功登記就不會再得到 3。不必假定中間每筆登記都成功，也不能據此指定另一個確切 ID。

`0x6adc8` 是稍後另一條路徑的重新讀取，不是登記回傳值的直接轉交；設定後投遞函式還會重新讀 `0x2000324b`。本結果沒有證明所有寫入者、兩次讀取間不受干擾或實際安裝的 ROM。下一個可縮小的條件：`0x6ae4e` 會依共用 ID 是否為 255，決定是否寫入阻止選項 8 尾跳的 byte `0x200035ab`。
