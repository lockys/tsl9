# 寫回呼收到哪一列？

**V1.31 參考實作按 handle 重新查找，但回傳原陣列中那一列的地址，不是列內容的複本。** 註冊時複製的是 8-byte 服務描述資料，包含原屬性陣列指標；服務節點的 `+4` 是 count，`+8` 是該指標。回呼表另行登記，不是屬性陣列。

- 寫入例程 `0x4bb26..0x4bb48` 將入口 `a1` 當作待查 handle，另傳 `sp+30` 作輸出位置。AUIPC/JALR 的目的為 `0x20000a48`。依參考啟動碼的 RAM 映射，此函式來自 carrier `0x40cb8`，不是直接從 APP 讀取。
- 查找從 `[0x20002f88]` 開始。每個節點讀陣列首列的半字 handle `first=[attrs+10]`。對 16-bit 輸入，僅在 `first <= handle < first+count` 時進列掃描；**仍逐列比較 `row+10`，並非直接用 handle 差當下標**。`0x20000a76` 先把當前列指標留在 `a2`，然後指標加 16，從新指標 `−6` 讀原列的 handle。相等時若輸出指標非空，寫回的是 `first`；`0x20000a88` 以 `a0=a2` 返回原列。掃完未命中會查下一節點，走完整串列無命中則返回零。
- `0x4bb50` 保存查找結果到 `s1`。用首 handle 另查回呼表後，`0x4bb6c` 令 `a1=s1`，`0x4bb70` 呼叫表的第二個函式。因此若節點仍指原 APP `gp`、匹配列為下標 3、回呼仍綁定 `0x888c`，則收到 `0x20004030`，而 `+12` 的初值為 `0x20004080`。不證實機執行、唯一服務、RAM 未被改寫或目前 handle 數值。

驗證：對 SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22` 的參考區段，以原始指令長度切開 `0x20000a48..0x20000a94`；查核 call target、保存／恢復列指標、讀半字與返回；用 4 列有序、重排、重複及缺號的合成表對照有限指令執行。不把合成表當作裝置內容。
