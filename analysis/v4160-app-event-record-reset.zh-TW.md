# v4.1.60：APP 事件記錄基址的 reset 來源

接續[事件參數資料流](v4160-app-event-record-byte.zh-TW.md)。本輪驗證 `[gp+104]` 的初始值，不把 reset 快照當成事件處理時的實際狀態。地址為 APP 執行位址，BIN 檔案偏移須減 `0x8000`。

| 原指令／資料 | 核對結果 |
| --- | --- |
| `0x186aa`／`0x186ae` | 建立 `gp=0x20004000`。 |
| `0x186ba..0x186da` | 從 `0x1ab60` 逐 word 複製 128 bytes 到 `[0x20004000,0x20004080)`；第 27 個 word（零起算索引 26）來源是 `0x1abc8`。 |
| `0x1abc8`（BIN offset `0x12bc8`） | Little-endian `94 c6 00 20`，因此寫入 `[0x20004068]` 的執行期指標初值是 `0x2000c694`。 |
| `0x186de..0x186f4` | 清零 `[0x20004080,0x2000c958)`，不清指標欄本身；但覆蓋 `0x2000c694` 起連續 256 bytes。 |

獨立交叉引用：`0x13064`／`0x13068` 直接建立 `a1=0x2000c694`。前綴由 `[0x4004c]` 取間接函式，傳 `a0=sp`、`a2=256`，在 `0x1306c` 呼叫。這證明另一個 APP 呼叫點以同一地址作第二個參數；若該函式遵守已分析的複製方向，這是讀出端而不是載入端，不能據此宣稱已有記錄寫入者。

以原 BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 重播：Python `-O` 驗證 32 個 reset copy words、上述指標、目標前 256 bytes 的 64 筆清零覆蓋，以及 `0x13064` 位址對；全部通過。這是成功完成 APP reset 的靜態投影，不證設備生命週期、實際 provider、記錄容量或之後的寫入內容。

下一步先區分 `0x2000c694` 作來源與作目的的 APP 呼叫點，找出清零後首個可驗證的資料來源。未修改 BIN 或正式來源。
