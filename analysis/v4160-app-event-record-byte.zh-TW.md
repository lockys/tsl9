# v4.1.60：APP 事件參數的 `sp+14` 來源

接續[事件表與參數核對](v4160-app-event-table-arguments.zh-TW.md)。本輪只追寫入來源，不擴大表長假設。以下均為 APP 執行位址。

- `0x176f8` 建立 48-byte stack frame。`0x17780..0x177a0` 向 `[0x4004c]` 的間接函式傳入 `(sp+8, load32(gp+104)+7*load8(gp+376), 7)`。**若**它依此參數執行 byte copy 並正常返回，第七 byte 會到 `sp+14`，來源為該選定記錄 `+6`。
- 若 `0x177a2` 重讀的 `gp+376` 非零，且 `byte[sp+9] & 0xfc == 0`，APP 先清 `gp+376`，再於 `0x177c2` 重新透過同一個槽呼叫，來源改為重讀的 `load32(gp+104)`。若第二次同樣執行完整 copy，則 `sp+14` 改由第二次來源 `+6` 決定；不能假定兩次讀到相同基址或函式指標。
- `0x177c4..0x177de` 要求 `sp+9` 的 bit 1 設定，並依 `load32(sp+8)` 的 bits 10..15 分路。值 1 走 `0x177ee`，值 2 才走本輪的 `0x17832`；前者的 `0x17812` 不屬於後者的這條路徑。表處理對 frame 的明確寫入是 `SW sp+8`、`SB sp+12`，都不碰 `sp+14`。若 SP 保持、其他寫入不別名且無干擾，最後一次 copy 的第七 byte 保留至 `0x1786c`。

原 BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。Python `-O` 核對 12 個指令窗及兩個解碼分支目標，並通過七個表值 × 256 個來源 byte，共 1,792 組合成向量。向量採已完成且符合分支條件的 copy 結果，不是 CPU 模擬、不是 provider 實作或實機可達性證據。

下一個檢查點：優先找 APP 中 `gp+104` 的初始化及指向記錄的寫入者，再區分七 byte copy 假設和 resident 版本證據。未改 BIN 或正式來源。
