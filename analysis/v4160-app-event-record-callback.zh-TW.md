# v4.1.60：事件記錄描述子的回呼資料方向

接續[四處指標引用](v4160-app-event-record-references.zh-TW.md)，這輪只追 `0x1376c` 建立的描述子，不推斷完整排程或實機行為。

1. `0x13794/0x13798` 建立回呼 `0x13f36`，`0x1379c` 將它與描述子交給 `0x9124`。若之後確實以該描述子呼叫，`0x13f40..0x13f4e` 取 `+8` 的長度與 `+4` 的指標，再呼叫 `0x13e98`。指標是在建立描述子時保存，不是回呼執行時重讀 `gp`。
2. 若這兩個欄位仍是原先的非零記錄指標及長度 256，`0x13e98` 轉到 `0x13b4c`。後者把長度給 `[0x40070]`；若回傳零，就不進入複製區塊。若回傳非零，且續段的暫存器及堆疊欄位保留，`0x13b76` 透過 `[0x4004c]` 傳入 `(剛回傳的指標, 描述子保存的記錄指標, 長度)`，`0x13b80` 再把前者交給 `0x8a56`。若指標或長度為零，`0x13e98` 有另一條直接轉移路徑，不作相同推論。
3. 因此在候選 byte-copy 語意及兩區不重疊的條件下，這條路徑把記錄作為**來源**，不像 `0x14be4` 把記錄作為目的。這不是排除所有寫入的證據；間接提供者可能有副作用，實際配置、排程回傳與別名關係仍未知。

以原 APP BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 重驗：Python `-O` 通過四個原始指令窗、一個回呼位址對、五個 JAL 目標與四個合成複製／未複製投影。未修改 BIN、正式來源或設備。下一步回到索引，針對 `gp+376` 盤點直接寫入者，判斷 `0..35` 能否從單一寫入點推廣到讀取路徑。
