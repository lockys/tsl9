# v4.1.60：佇列過濾器如何處理記錄長度

接續[佇列記錄來源](v4160-app-event-object-queue-source.zh-TW.md)。核對原 APP `0x82d2..0x838e`，包括返回指令之後、仍可由內部跳轉抵達的第二輪掃描。

- `0x82ec` 把傳入記錄指標存到 `s1`。`0x8328` 讀記錄 `+2` 作為長度；符合轉送條件時，`0x8358` 重新讀同一欄位，`0x8362` 把加二後的值放在 `a3`，不是寫回記錄。
- 範圍內 13 條直接 store 都以 `sp` 為基址：11 條保存暫存器，兩條寫本地暫存區 `sp+4/+5`。若堆疊依已檢查的呼叫路徑向下配置且未被換掉，這些位置不與 caller 的 `sp+8` 記錄重疊。這個指令盤點不排除外部呼叫副作用。
- `s4` 起始為零。候選項目若通過前三個選擇條件，`0x832c` 會先把非零選擇值寫入 `s4`，才做長度 `<=8` 檢查。因此長度過大可以不轉送但仍回傳非零；不能把 `<=8` 當成後續功能分派的長度上限。在沒有外部狀態干預、兩輪都未選中項目的路徑上，沒有執行 `0x8356`／`0x8368` 的呼叫，過濾器返回零，記錄長度不被它改寫。APP caller 隨後仍需通過其他條件才會進入功能分派器。

Python `-O` 通過原 APP SHA-256、188 bytes／69 條指令、13 條 store、兩處長度讀取及兩個呼叫點的核對。未執行實機或外部函式。下一步沿佇列槽的正常填入路徑追查 `+2` 的寫入來源。
