# TSL9 傳送入口與原生呼叫框架

[English](readme.en.md)

本輪繼續重建官方 ID2966 V4.1.60 的 OTA 傳送函式 `0x8A56..0x8B6E`，目標是讓可讀 C/C++ 真正符合原始入口、ROM 呼叫與記憶體時序。原始映像 SHA-256 為 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。**目前不構成原硬體或藍牙 OTA 相容性證明。**

## 已取得的實際證據

原始 280 bytes／96 條指令的契約沿用已核對的來源解碼器。本輪另外核對長度拒絕路徑、五個暫存器儲存及成功路徑的分段還原。原始碼說明位於 [source-review](source-review/README.md)，獨立機器碼檢查位於 [ABI-review](ABI-review/README.md)。

兩個普通 C 分支提示讓原生候選恢復兩次 ROM 呼叫的返回位址 `0x8A90`、`0x8AB6`，但單獨編譯仍在拒絕超長輸入前配置堆疊。實際合成診斷排除了「移除 memory clobber 即可修復」及「全域 register 宣告即可擁有框架」兩個不足的解釋，詳見 [編譯器診斷](entry-plan/README.md)。

窄入口由兩條標準組語指令及標準 ELF `R_RISCV_BRANCH` 重定位構成，主體及返回葉函式仍由 C11／C++17 編譯。兩種語言的實際連結配置均為：

| 部分 | 起始位址 | 大小 |
| --- | --- | --- |
| 真實入口 FUNC | 0x8A56 | 8 bytes |
| 可讀 C/C++ 有效輸入主體 | 0x8A5E | 270 bytes |
| 真實 C/C++ 返回葉函式 | 0x8B6C | 2 bytes |

三者相鄰，整個配置為 280 bytes；入口的公開 FUNC 如實保留 8-byte 大小，沒有把 metadata 偽裝成單一 280-byte C 函式。超長輸入只經過設定 A5、無號分支及 RET，沒有堆疊或記憶體存取，也沒有新 RA 連結。這是窄組語移植層加上 C/C++ 主體，不是純編譯器輸出或完整原函式組語複製。

迴圈亦已比對實際機器碼的控制流程：原始 BLTU 的 true 分支對應候選 BGEU 的 false 分支；兩者保留低 16 位計數比較、live S0、八條 payload 指令及回到相同計數標頭的 backedge。每種語言各拒絕九個實際指令位元反例。這項證明以對應的標頭暫存器及記憶體回應為前提，不涵蓋非同步干擾或把被替換程式碼本身當 payload 讀取的情形。

## 尚待通過的條件

成功路徑需要在 descriptor 半字寫入之前 freshly 還原 RA／S1／S2／S3，之後還原 S0，最後才在任務位元組讀取之後回復 SP。原生編譯器把這些還原集中到結尾，可能改變與框架重疊的記憶體讀值。本輪已用獨立、範圍明確的排序步驟修正：只重排本次編譯的五個儲存及五個還原指令，C/C++ 的實際輸出均通過獨立檢查，其他 ELF 位元組與 metadata 不變。這些時序界線通過，不代表整個函式或任意非同步行為已等價。

原機 ROM 的真實保存規則、實際堆疊可達範圍、未知間接入口、晶片與周邊、BOOT／更新器接受規則及救援路徑仍未全部證明。此元件尚未納入完整映像。完整映像仍維持上一輪的 12 個可讀函式／650 bytes；本輪沒有新的可刷寫 BIN。

封存與結果中的「通過」只適用於各自列明的靜態條件。產物只作資料檢查，不執行或模擬 RV32，不操作 BLE／CAN／Flash，不呼叫廠商服務。重建目標仍是可由原藍牙 OTA 更新的原機韌體，並未縮減為 HOST 模型。

可新增功能的既有提案包含離線封包預檢與更新等待原因顯示；它們仍是[提案](../v4160-ota-tx-2026-10-22/continuation-plan/README.md)，不是已燒入硬體的功能。
