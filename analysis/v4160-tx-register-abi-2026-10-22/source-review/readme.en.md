# TX entry, stack and typed-source constraints

[繁體中文](readme.zh-TW.md)

This is a source-contract review for repairing the readable native TX port. It reuses the immutable original `0x8A56..0x8B6E` proof (280 bytes, 96 instructions). It neither admits a new replacement nor repeats unchanged HOST suites. `check-source.py` reads the exact original ID2966 image, verifies the old sealed decoder/contracts, checks 21 entry/restore boundary records and rejects seven actual-byte mutations. Its PC-specific checks authenticate the original obligations; they are deliberately **not** a general semantic equivalence checker for future compiler output.

## Minimum observable obligations

The original first writes A5=1039, then uses unsigned `A5<A3` at `8A5A` to branch to the early RET at `8B6C`. On oversized input, A0 and SP retain entry values; there is no stack store, GP load or opaque call. A native compiler prologue before this guard introduces real stores even if the LLVM IR has the C branch before its first volatile access. An unavailable stack or a memory observer can distinguish the paths. Successful HOST testing does not establish that the invalid-entry stack is always writable.

On a valid input, SP decreases by32 at `8A5E`, then `8A60/62/64/66/68` save S0/S1/S2/S3/RA to offsets24/20/16/12/28. The first GP-dependent handle load follows at `8A6A`. Reordering these five disjoint saves can preserve their final memory contents in a quiet, non-faulting case; exact fault/interruption prefixes are stronger obligations. The invalid path's added stores cannot be dismissed as merely a save-order difference.

On success, `8B26/28/2A/2C` freshly load RA/S1/S2/S3 **before** the metadata SH stores at `8B32` and `8B36`. S0 is freshly loaded **after** those stores at `8B40`; the slot32 load at `8B46` and unsigned byte handle at `8B4A` follow, then live SP increases by32 and `8B50` jumps through T1 without a new link. Moving all restores to a conventional epilogue crosses alias-capable memory effects. Correct ordinary return values alone do not prove this order interchangeable.

The source-backed alias witness is aligned: live SP=`0x2000B170`, entry SP=`0x2000B190`, fixed buffer B=`0x2000B18C`, hence saved RA at SP+28 equals B. With saved word `0x12340003` and stable length1, the metadata SH at B+2 stores7. An early RA load obtains `0x12340003`; a late reload obtains `0x00070003`. Header, payload and checksum writes start beyond this word. This is interval and little-endian halfword algebra, not execution or a claim that this SP is reachable on the physical device. Importantly, standard callee SP/S preservation alone does not exclude it: the entry SP could already have that aligned value.

Two slot calls link at `8A8E` and `8AB4`, creating raw RA=`8A90` and `8AB6`. Unknown callees can observe link addresses; changing those addresses is a substantive ABI gap until a narrower callee contract is established. The second call receives ambient A2/A3 residues from the first call, not freshly restored source/length arguments. GP, S registers and SP are reread by the original dataflow; no identified ROM signature or preservation rule is proved.

## What the old C/IR establishes

The old native macros make `TX_FRAME`, frame restores and pop no-ops, so LLVM owns the actual prologue/epilogue. The selected old IR has the length branch before its first volatile handle load, but the actual old object still begins with SP−32 and five saves. Thus IR lexical order is insufficient to place compiler-created frame accesses.

`TX_FIXED` binds a register **at an asm operand**. An empty volatile asm with a memory clobber does not reserve that register throughout the function, prove adjacency to the next instruction, or pin an implicit frame layout. `TX_OBSERVE` uses an output-only asm operand: the C variable has an asm-produced definition, so it should not simply be diagnosed as an ordinary uninitialized C read. However, the abstract output does not establish that an intended earlier value survived intervening compiler allocation; actual machine evidence remains required.

The inline `jalr` exposes A0/A1/A2/A3/A5 outputs and caller-saved clobbers, but omits S0/S1/S2/S3/GP/SP. That leaves preservation assumptions in the compiler interface. Adding fresh observations does not make the compiler's own spills and restores robust to an arbitrary changed SP. The source-level numeric HOST provider intentionally has broader opaque state mutation than an ordinary C call ABI; its passing traces do not transfer that guarantee to native code.

Typed `volatile uint16_t` and `uint32_t` accesses have alignment and target-memory validity assumptions (the retained IR carries align2/align4). Ordinary C unsigned arithmetic wraps as intended, but volatile and a memory clobber do not remove pointer/alignment requirements or order hidden compiler frame accesses. Synthetic unaligned numeric HOST fixtures are not evidence of defined physical C accesses. No new blanket undefined-behavior accusation is needed: the concrete frame-order and callee-contract gaps already block admission.

## Bounded implementation choices

1. **Frameless typed dispatcher plus typed body:** first probe a dispatcher that needs only entry A0..A3/A5, performs the guard, and `musttail` transfers valid input to a separately compiled body. Actual emitted evidence must show no dispatcher frame/spills, exact argument and early-return residues, a truthful returning type, real tail transfer, bounded total ownership and correct incoming/private roles. The extra branch/body boundary is not automatically transparent, and fitting both pieces in280 bytes is unproved. An asm guard inside the existing framed function does not by itself constrain where its prologue goes.
2. **Explicit numeric-SP/frame custom port:** a small frame/terminal intrinsic can be examined under a pinned toolchain, but a C body ending with RET/JRT1 asm plus `__builtin_unreachable` is not an ordinary returning C function. LLVM may infer `noreturn` even without a spelled attribute. A typed caller or LTO could then discard continuation code although the physical RET returns there. Such a port requires a clearly separate machine-entry interface, no ordinary C-call exposure/LTO assumption, and actual proof of no hidden frame/spills/epilogue. Manual SP changes remain outside ordinary compiler stack assumptions. This is a possible target-specific extension to audit, not a portable-C solution or an established ABI repair.
3. **Reserved-register ownership is not established by a flag:** the installed Clang help describes `-ffixed-xN` as reserving the register, without stating that an asm may omit actual clobbers. The old retained IR already has `+reserve-x8/x9/x18/x19`, yet explicit outputs still lead to callee-save code. Removing those outputs would hide effects from IR. A custom profile with truly exclusive registers might be machine-auditable, but allocation exclusion alone cannot certify a defined ordinary extended-asm contract; RA/SP also participate in implicit control/frame lowering. The parent's bounded `entry-plan/global_owned_s0.c` probe is useful counterevidence: actual C and C++ IR use `llvm.read_register`/`llvm.write_register`, but both inspected 16-byte objects still save S0 in an SP−16 frame and restore it before RET. This probe was compiled by the parent and statically inspected here; no target was run, and global register syntax did not establish frame ownership.
4. **Do not repair by labels alone:** original byte copying, whole-function assembly, padding, renamed numeric aliases or a save-order permutation of a different instruction inventory would not establish readable-source semantics. Prefer one bounded source/profile probe and inspect its actual output; do not infer success from flags, size, source annotations or the existence of a `musttail` token.

Commutative ADD/MUL operands, a moved but correctly resolved PCREL pair, or equivalent branch predicates may be semantically acceptable with separate destination/control proofs. Whole opcode identity is stronger than necessary for some interface claims. Conversely, moving stores onto the rejected path, moving RA loads across potentially aliasing writes, or changing a callee-visible link value are actual behavior changes under the currently unbounded interface. Computed/interior entries, actual stack reachability, ROM behavior, asynchronous state, hardware and OTA acceptance remain unknown.

## Actual bounded source-hint outcome

The new canonical source differs from the old algorithm only by two `TX_EXPECT` wrappers around existing comparison results. The HOST macro is the identity and reuses the old immutable provider; the native macro adds branch expectation metadata. The checker independently verifies this exact source delta. There is no new HOST algorithm to revalidate in this source scope. Both actual canonical objects were statically read:278 bytes/95 instruction geometries, second gate at relative `+0x5E` (raw link `8AB6`) and PCREL high anchor at `+0x80`. The first instruction still adjusts SP, so this improvement does not close the early-guard obligation or late-restore alias gap. The remaining two bytes are not declared free or padded. Retained parent compilation observations are distinct from fresh raw/source checking and do not become an implicit artifact replay on a transported checkout.

## Actual narrow entry adapter

The returning C dispatcher probe was also inspected:18-byte entry plus272-byte body exceeds the280-byte owner. The next implemented option uses exactly two authored assembly mnemonics, a real typed valid-only body and a real typed identity-return leaf. A direct external assembler branch initially expanded to BGEU+JAL:12+270+2=284 bytes, so that output was rejected. The approved revision uses an assembler-authored BLTU placeholder and exactly one standard `R_RISCV_BRANCH` relocation to the real C leaf. There is no opcode encoder, copied original instruction, byte directive, padding or whole-function assembly.

Both actual revised C/C++ component pairs were independently inspected:entry8, body270 and leaf2 are contiguous at `8A56`, `8A5E` and `8B6C`. The linked guard at `8A5A` really targets the typed RET at `8B6C`; before that rejected-path RET only A5 is assigned1039. A0/RA/SP remain untouched, there is no memory access or new link, and the frame exists only on the valid fallthrough. Entry.o contains exactly one branch relocation at+4; the leaf IR returns its actual context parameter and its machine code is only RET. Five actual-code controls per language reject a wrong limit, signed guard, wrong branch target, changed A0 destination and a link-writing leaf. The body extraction and five separately labelled source-text controls are also checked. Source-text controls are not compiled semantic negatives.

The public assembly symbol honestly has FUNC size8, the valid C body270 and typed leaf2. This differs from the original FUNC280 metadata role; it remains an integration-role obligation, **not** an established runtime failure. No fake extent/alias is substituted. This pre-motion adapter still has late success restores and a different save order. It is not a complete ABI repair or full image. The numeric SRAM PCREL witness is checked as a numeric target only, without supplying a real memory/provider implementation.

The concrete next implementation is a separately declared load-order pass over the five existing compiler-generated LW-SP words:move RA/S1/S2/S3 before the two metadata SH operations, and restore S0 only after the live length+6 value is consumed by those stores. The pass must prove no intervening SP write, opaque call, remaining destination-register use, branch/interior entry or relocation is crossed incorrectly; retain all other instruction order and source/object identities. Merely changing five locations without retaining a complete permutation/provenance proof is insufficient. Such an output is explicitly **C/C++ plus a native scheduling pass**, not pure Clang output or an ordinary C-interface guarantee. Its admission is separate from this sealed original/source contract. Original save-order/fault prefixes, unknown ROM behavior and arbitrary SP changes remain separate constraints.
