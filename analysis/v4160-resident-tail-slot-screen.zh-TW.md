# v4.1.60：尾呼叫表槽 0x400fc／0x4011c 的靜態篩查

接續[上游來源分析](v4160-resident-tail-copy-upstream.zh-TW.md)。目的：找出另一個 wrapper 的上游呼叫是否提供指向 resident 欄位的來源指標，而非把相同的指令位移誤認成同一個表槽。

以 SHA-256 核對 v4.1.60 APP 與 V1.30／V1.31 參考映像，在 APP 原址與參考映像 `0x40000` 基址上掃描半字對齊的指令候選。搜尋 `LW` 位移 `252`／`284`；另對 `LUI`／`AUIPC` 後 64 bytes 內的同基底 `LW`／標準 `C.LW` 做數值篩查，並納入一條 `ADDI` 後緊接讀取的形式。這是原始指令候選篩查，不驗證所有基底暫存器的活值或可達性。

| 映像 | `LW +252`／`LW +284` 候選數 | 落到兩個目標槽的近距離位址候選 |
|---|---:|---:|
| v4.1.60 APP | 0／0 | 0 |
| V1.30 | 5／1 | 0 |
| V1.31 | 5／1 | 0 |

正對照：APP 已知 `0x0bee` → `0x0c0c` 的 `0x400d8` 讀取被找回。兩版參考映像的六個原始位移候選均使用 `s0`，不是已驗證的表基址。例如 V1.31 `0x59f24` 周邊先寫同一個 `+252` 欄位，再讀回並存到 `+268`；`0x6a6d4` 的 `+284` 讀取後接 `sw a0,0(a5)`，不是直接間接呼叫。Python `-O` 的三映像檢查均通過。

結論：這次沒有找到能解析 `a1` 的呼叫點，**不能排除**較遠的暫存器傳遞、動態索引、表槽複製或其他載入形式。下一輪應先查是否有複製或轉傳整張表的路徑，再追被轉傳表基址的呼叫點；若仍缺少來源證據，將該分支保留為未解析，不推斷它是否讀取 `+244..255`。
