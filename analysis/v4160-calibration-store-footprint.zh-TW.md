# 首次校時：0x1929a 的直接寫址

`0x19ba8` 呼叫 `0x197b8`；後者以 3 尾跳校準函式，不再配置 stack。從原 APP（SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`，載入基址 `0x8000`）以 RV32 反組譯 `[0x1929a,0x196c4)`，共 329 條指令。以下是靜態 store 位置數，不是執行次數；不要求輪詢一定結束。

| 寫入目標 | 寬度 | 指令位置數 |
|---|---:|---:|
| frame SP+12，以及 SP+28 至 +76（每隔 4） | 4 | 14 |
| `0x40022036` | 2 | 3 |
| `0x40022049` | 1 | 6 |
| `0x4002204c` | 2 | 15 |
| `0x4002204f` | 1 | 12 |

外設基址取自 `lui ...,0x40022`。四個 `sh ...,32(a5)` 不是寫 `0x40022020`：在 `0x1945a`、`0x19596`，a5 已設為基址 +44，再加 32 才是 +76。`[gp+108]` 是算術輸入，不是寫入目的指標。六個直接呼叫均為先前核對的唯讀 `0x191c6`。

沿用[兩次 RTC 設定](v4160-clock-rtc-setters-task-fields.zh-TW.md)的 `0x9008` 入口 SP 假設，校準 frame SP 為 `0x2000ff90−80=0x2000ff40`。實際可能寫的 stack bytes 為 `[0x2000ff4c,0x2000ff50)` 與 `[0x2000ff5c,0x2000ff90)`；這 56 bytes 不碰任務數量／容量 `[0x2000319d,0x2000319f)` 或 APP 首次任務 ID `0x20004184`。此為直接位址分離，非設備 MMIO 副作用、實際堆疊或排程狀態不變的證明。

重現：用 `rasm2 -a riscv -b 32 -s 0x1929a -D HEX`，HEX 為原檔 `[0x1129a,0x116c4)` 的十六進位字串；片段 SHA-256 `0b79dfccf11a0f49b7d234d0efdd318c2d564ff95e4d8711c12aee0fb963a236`。統計 `sw/sb/sh` 並追蹤各 store 的基址。正常返回後 `0x19bae/0x19bb8/0x19bc2` 寫 caller SP+4/+8/+0；這三筆並未定義 SP+12。接下來須分辨傳給 `[0x40074]` 的第四個 word 從哪裡來，以及候選 provider 是否使用它。
