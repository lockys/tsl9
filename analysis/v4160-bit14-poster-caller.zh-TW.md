# 何時呼叫 bit 14 投遞函式？

接續[目的 task ID 的來源](v4160-bit14-resident-poster.zh-TW.md)。V1.31 參考 carrier（SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`，檔案偏移加 `0x40000`）可區分兩道條件：上游決定要不要呼叫投遞函式，投遞函式才讀目的 ID。

| 參考 PC | 原指令證據 | 局部效果 |
|---|---|---|
| `0x4fe5a` | `ef206038` | 呼叫 `0x521e0`。 |
| `0x4fe5e`, `0x4fe60` | `aa89 1de1` | 保存其回傳值至 `s3`；`a0 != 0` 跳往 `0x4fe86`，略過投遞。 |
| `0x4fe62..0x4fe7e` | 四個 `sb`，接著 `9700fb1f e7800061` | 零值路徑先寫 `s1+0..3`，再以 `a0=s1+4, a1=sp+8, a2=8` 呼叫 `0x2000048a`。目的資料不等於目的 task ID。 |
| `0x4fe82` | `ef509f88` | 上一呼叫若正常返回，此處直接 `jal ra,0x4570a`，不測它的回傳值；返回位址為 `0x4fe86`。 |

以每兩個位元組為起點掃描參考檔的 JAL、C.J、C.JAL 位移，指向 `0x4570a` 的編碼只找到 `0x4fe82`，並以鄰近指令反組譯核對。這不是完整呼叫圖：不排除間接呼叫、不同入口或其他映像。上游回傳零是走到此呼叫點的條件，**不是目的 ID 為 3 的證據**；先前已識別的半字初始化會把 ID 設為 255。尚需找出其他初始化或設定目的 ID 的來源，不能據此稱 task 3 已收到事件。
