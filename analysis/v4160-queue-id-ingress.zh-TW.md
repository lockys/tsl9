# v4.1.60：記錄佇列的兩條已知來源

離線靜態分析原始映像 SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`，位址為載入基址 `0x8000` 後的位址。

- `0x12c58` 憃描 `0x2000c038` 起的 32 筆、每筆 12 bytes；首 halfword 為零的槽不被當作有效記錄。
- `0x12bc8` 找第一筆首 halfword 為零的槽，依序寫入 ID 低 16 位、長度低 8 位，透過 `0x4004c` 間接呼叫，正常返回後寫入 tag。此函式本身沒有 11-bit ID 或長度不超過 8 的檢查。未知 provider 的副作用與暫存器保存未確認；ID 零與空槽標記相同。
- `0x16afa` 是一個直接呼叫點：`0x16a7c` 路徑檢查輸入 byte 1 的 `& 0x18` 為零及長度低 nibble 為 1–8，組合 ID 為 `(byte0 << 3) | (byte1 >> 5)`。十進位 325 (`0x145`) 的例子是 `28 a0`，十進位 925 (`0x39d`) 是 `73 a0`。二者在算術上可表達，並不證明實際收到或成功入列。
- `0x12c4a` 是另一直接呼叫點：`0x12c24` 先呼叫 `0x18d78`，然後從局部結構讀取 ID 和長度。擴充格式分支寫入不同欄位，不能據此推斷呼叫者讀到的 ID。

上述來源未排除其他間接入口或外部寫入。尚無裝置接收、實際 resident、provider 複製成功、中斷同步或排程執行證據。`analysis/check_v4160_queue_id_ingress.py` 僅檢查原映像身分、兩個消費端指令窗及兩個 ID 算術見證，並不獨立驗證上面全部控制流程。
