# `0x5362e` 清零後的呼叫：哪些會直接寫入 role 計數？

接續[初始化入口](v4160-role-count-earlier-registration.zh-TW.md)。目標是 `0x4daf6` 所讀的 `0x20003350`；以下只針對 V1.31 參考 carrier，未執行裝置。沿著 `0x53650` 的 296-byte 填寫正常返回後的呼叫順序核對：

| 呼叫或尾跳 | 核對結果 |
|---|---|
| `0x5365a → 0x55bd4`、`0x53660 → 0x55c48` | 兩個呼叫前各設 `a0=0`。兩個 leaf 各寫一個 word，位址為 `0x200034e0`、`0x200034e8`，隨即返回。 |
| `0x536fe → 0x43e24` | 只讀 `0x2000323e` 的 unsigned halfword，依 `<=20/30/50/75/100/150` 依次返回 7 至 2；151..250 返回 1，251 以上返回 0。完整 callee 沒有 store 或子呼叫，不能據返回值推定目標 RAM。 |
| `0x537b2 → 0x64298` | 非 leaf，涉及 RAM、外設位址與後續呼叫；未排除整條路徑。 |
| `0x537b6 → 0x57ac4` | 固定參數尾跳至 `0x2000039c`，名義清零 `[0x20003454,0x20003470)`，不含目標。 |
| `0x537ba → 0x63704` | 清除 `0x2000347c` 的 word 及 `0x20003478` 的 byte，返回。 |
| `0x537c8 → 0x5e758` | 先清除 `0x20003480` 的 byte 及 `0x20003484` 的 word，**再尾跳 `0x53868`**；不能當成只寫兩處即返回。 |

這六個直接 store、固定填寫及唯讀分類函式均不能直接改掉目標。這不是整個父函式或所有路徑的無寫入證明；尚須區分 `0x64298`、`0x53868` 及其子呼叫的作用，也未檢驗硬體副作用、實機 ROM 或 live RAM。

`python analysis/check_v131_role_postclear.py <V1.31-reference-carrier>` 固定映像 SHA-256 與六段指令窗口，解碼八個 JAL（區分 call 與 tail）、六處儲存位址/寬度與清零參數。分類門檻依完整窗口靜態反組譯，不是指令模擬。普通與 `-O` 均通過。
