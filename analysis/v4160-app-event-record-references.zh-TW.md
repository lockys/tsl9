# v4.1.60：APP 事件記錄指標的四處直接引用

接續[記錄更新](v4160-app-event-record-update.zh-TW.md)。在固定 SHA-256 的原 APP BIN 中，每半字位置篩選 32-bit `ADDI`／整數 load 的 `gp+104` 形式，以及直接以 `gp` 為基底且覆蓋指標欄的 `SB/SH/SW`。前者有四處，後者無命中。這不是完整的 writer 證明；reset 就透過 `a1` 間接寫入此欄，其他別名及間接函式也不在篩選範圍。

| 指令位置 | 局部資料流 |
|---|---|
| `0x1376c` | 依 `a1` 選 `[gp+104]` 或 `[gp+100]`，把讀出的指標放進描述子的 `+4`，把 `256` 放進 `+8`。這裡是指標傳遞；尚未分類後續回呼對指標所指記憶體的用法。 |
| `0x14be4` | 把讀出的指標作為間接複製函式的第一個參數；是先前查到的條件更新點。 |
| `0x167e6` | 後續在 `0x16814` 讀指標、加記錄偏移，再讀前兩個位元組；符合局部條件時在 `0x16836` 呼叫 `0x1798a`，令 `a0=1`、`a1` 為記錄索引。 |
| `0x1778a` | 把讀出的指標用於七位元組記錄來源，再由同一段程式處理堆疊上的資料。 |

另核對 `0x1798a`：以 unsigned 比較排除 `a1 > 35`，而 `a0` 非零的分支在 `0x179e4` 將 `a1` 寫入 `gp+376`，供事件讀取路徑使用。`0..35` 的每個 `7*i+6` 都在 256 bytes 內；這只約束此寫入點，不代表 `gp+376` 的所有寫入者或全生命週期皆已驗證。

以 Python `-O` 通過九個原指令窗、四筆直接引用、直接重疊 store 篩查、unsigned 分支解碼，以及 256 個索引的偏移比較。未修改 BIN 或正式來源，未執行設備。下一步追 `0x1376c` 準備的描述子在回呼內如何使用，判斷是另一個寫入者或純讀取端。
