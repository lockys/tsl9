# v4.1.60：主迴圈派發晚於索引直接寫零

接續[初始化順序](v4160-app-event-selector-init-order.zh-TW.md)與[候選登記行為](v4160-app-event-selector-registration.zh-TW.md)。本輪追 APP 主線的第一個可辨識排程入口，不把它當成所有執行上下文的首次派發。

1. APP `0x900c` 先呼叫初始化 `0x9250`。沿前一輪已核對的 `0x928c → 0x17bf6` 路徑，`0x17c40` 呼叫 `0x1798a(1, 0)`，在 `0x179e4` 把零寫到 `gp+376`。同一分支到 `0x179f6` 才透過 `[0x40058]` 傳出 `(byte[gp+379], 2, 2)`；這個間接呼叫的語意不影響本段兩條指令的先後判定。
2. 初始化尾段跳至 `0x17b92`。若初始化及其下游都正常返回到 `0x900e`，APP 才呼叫 `0x8180` 進主迴圈：`0x818c` 設定 `s2=0x20000000`，`0x8198` 載入 `[s2]`，`0x819c` 間接呼叫。續段呼叫 `0x17002`、`0x12c58`，再由 `0x81a8` 回到 `0x8198`。
3. 若 RAM 第 0 項等於 V1.31 候選入口 `0x200007d0`，且候選程式已正確複製，`0x2000090a`（flash 來源 `0x40b7a`）從 handler table 取選中的指標後呼叫。只有成功登記、對應項目仍為 `0x176f8`、且排程選中該項目，才會由這條主迴圈路徑進入索引回呼。

結論：在上述正常返回主線中，**直接寫零先於首次主迴圈排程呼叫**。這不排除初始化期間的其他派發或間接寫入，也不證明第一次實際讀取 `gp+376` 時仍為零。下一步優先核對登記後、直接寫零前的 `0x90b0` 呼叫及其下游，釐清它是否可能同步執行回呼。

離線 Python `-O` 通過原 APP 與 V1.31 候選兩個映像 SHA-256、四個 APP 原始指令窗、七條直接控制邊，以及候選 handler 查表指令與 flash/RAM 位址換算。未連設備，也未修改原 BIN 或正式來源。
