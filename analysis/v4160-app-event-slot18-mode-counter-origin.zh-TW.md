# v4.1.60：模式計數的清零來源與累積條件

接續[計數門檻](v4160-app-event-slot18-mode-counter-gate.zh-TW.md)。本輪區分「從零可累積」與「實機會遇到相同回呼結果」。

- 原 APP `0x186aa/0x186ae` 建立 `gp=0x20004000`，`0x186de..0x186f8` 的 reset loop 清零 `[0x20004080,0x2000c958)`。若正常完成，位於 `0x20004140` 的四位元組清零涵蓋 `0x20004142`。若 GP 仍是同值，`0x10bba` 的 `gp+322` 正是此 byte；後續 `0x107c6` 把指標保存到 `s0`，並以該指標存取計數。
- 掃描原 BIN 全部 38,399 個可讀四位元組的半字起點，只找到一個位移恰為 `+322` 的 GP-based load/ADDI 編碼（`0x10bba`），無重疊的標準 GP-based SB/SH/SW 編碼。這是編碼盤點，不是完整寫入者證明；reset 和計數本身就使用其他基底暫存器。
- 假設從零開始，相鄰呼叫都使用同一計數位置及門檻 3，且其間未被其他路徑改寫，連續三次非零返回會走 `0→1→2→清零並進入寫入函式前的續段`。零返回會中斷累積。將八次回呼結果的全部 256 組合成序列逐步比對，計數與命中時點均符合這個規則。

Python `-O` 核對原 APP SHA-256、兩組位址指令、reset store 與回跳、讀寫指令、全 BIN 有限掃描及合成序列。未改原 BIN 或正式來源，未接設備。下一步核對 `0x1069e` 的資料來源與回傳條件，不把合成序列當作實機可達證據。
