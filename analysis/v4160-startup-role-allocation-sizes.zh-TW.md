# APP 啟動：兩筆配置只有一筆可能走小額游標

問題：計時器的 16-byte 請求之前，APP 的正常啟動程式是否還含其他可能取得小額區塊的呼叫？這裡只追一個 role 初始化入口，不列舉所有配置，不把靜態順序當作實際配置歷史。

原 APP `0x8eb2/0x8eb6` 自 `s0+416` 讀取後間接呼叫。若 `s0=0x40000` 且使用 V1.31 參考表，槽 `0x401a0` 指向 `0x6dd16`。先前呼叫正常返回時，`0x6dd2a` 直接呼叫 `0x4da70`，其中 `0x4dace` 先呼叫 `0x4edd2`。

| 配置點 | 長度與標記 | 候選游標選擇 |
|---|---|---|
| `0x4ee08` | `c=load8(0x20003201)`，`k=(c&3)+(c>>2)`；k 非零時請求 `60*k`，標記 `0x9001` | 正長度 60..3960，皆超過 52；名義 c=14 時是 300。k=0 跳過此呼叫。 |
| `0x4db10` | 前一函式及後續清零呼叫返回後，`0x4daf6` 讀 `n=load8(0x20003350)`；n 非零時請求 `16*n`，標記 `0x4c04` | n=1/2/3 分別為 16/32/48；n=0 跳過；n>=4 選大額游標。 |

兩個 AUIPC/JALR 都指向 `0x20000040`；候選 RAM 程式 `0x20000066..0x2000007b` 先將長度向上對齊至 4，再將無號對齊長度與 52 比較。上述長度已對齊且不會在 16-bit 截斷時溢位。`0x4dae0..0x4daee` 的名義清零範圍為 `[0x20003320,0x20003350)`，**不包括** n。不能由這次清零推斷 n=0，也不能直接使用設定欄位 c 代替 n。

驗證：核對 APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`、V1.31 carrier SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`；以 rasm2 檢視兩段載入、分支及參數算術，另解碼兩條直接呼叫、兩組配置器位址、核對門檻指令，窮舉 c、n 各 256 值，一般及 Python -O 均通過。候選指令集和啟動複製仍是前提；沒有觀察到實際配置、成功返回、實體節點或裝置 ROM。下一步為查找 `0x20003350` 在此讀取之前的寫入來源。
