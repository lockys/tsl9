# 在 role 計數讀取前：登記函式與 296-byte 清零

接續[配置區寫入界限](v4160-role-payload-count-bound.zh-TW.md)。這次從讀取者的上層倒推，而非把整份 ROM 中相似的立即數都當成寫入來源。

V1.31 候選 `0x6dd16` 先經 `0x6dd1a → 0x61b1c`、`0x61b20 → 0x55bde`。後者讀 `0x2000319f`，若為零才依序呼叫 `0x43c4e`、`0x5362e`。外層正常返回後另有 `0x6dd26 → 0x43c4e`；再經 `0x6dd2a → 0x4da70` 才進入含 `0x4daf6` 計數讀取的函式。

- `0x43c4e` 是登記，而非同步執行 handler。在 Xwchc 解讀下，無號索引 `i` 及容量都是 byte；`i >= capacity` 不寫，成功才改 `0x2000319d` 並向 `table+4*i` 寫一個 word。不要把登記用索引當成目標 `0x20003350`。
- `0x43be2..0x43bf5` 從配置指標欄位重新載入 P，將 `P+576` 存入表指標 `0x200031c4`。若 P 仍是名義區內有效配置且表指標未遭改寫，最小 slot 寫址是 `0x200045f4`；所有成功組合都高於目標且不會繞回。本結論只回答是否命中一個 byte，不是整張表的容量或有效性證明。
- 可選呼叫 `0x5362e` 中，`0x53650` 呼叫候選填寫程式 `0x2000039c`，清零 `[0x200033b8,0x200034e0)`。起點在目標後 104 bytes；另一次 `0x5364a` 的直接 word 寫入是 `0x200034e4`，也不包含目標。

重現：`python analysis/check_v131_early_role_registration.py <V1.31-reference-carrier>`。核對 SHA-256、6 個 JAL、4 段指令、65536 組索引/容量和清零範圍，普通與 `-O` 均通過。不排除該函式後段、其他呼叫、非名義表指標或外部硬體寫入；不能據此宣稱讀到零。
