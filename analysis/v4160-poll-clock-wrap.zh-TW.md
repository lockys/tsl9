# 原始 RTC 回零與商低字回繞是兩件事

接續[原始樣本到輪詢值](v4160-rtc-to-poll.zh-TW.md)。對 V1.31 參考服務，令 `Q(x)=low32(floor(1600*x/d))`。若 `Q(x)<last`（無號比較），`0x43db6` 重讀設定字 B 並換算 `W=Q(B)`，增量是 `low32(W-last+Q(x))`，沒有額外加一。這是比較商的低字，不直接比較 RTC 樣本。

- 若沿用 APP 傳入的設定 `d=16000,B=0xffffffff`，全範圍內的商最大只有 429496729，不會溢出 32 位。原始樣本 `0xffffffff → 0` 時，舊商恰等於 W，新商為零。last 改寫為零，但累計字雖寫回卻不變；這次轉換本身不增加 APP 時間差。不是說一個更早開始的等待必然尚未逾時。
- 合成前置條件：回零前以累計字 0 為輪詢基準，回零後逐一讀 0..60，沒有干擾。第一個滿足無號時間差 >2 的樣本仍是 50；這不是毫秒或硬體保證。
- 反例對照：若改用非標稱 d=1，原始樣本 `2684354 → 2684355` 是遞增的，但商低字從 `0xfffffc80` 變 `0x2c0`，走同一個向後分支。B 為 `0xffffffff` 時增量為零；控制組只改 B 為零，增量變 1600，從累計字 0 得到 APP 差值 1000。不能單從這個分支斷言 RTC 曾回零。

`python analysis/check_v4160_poll_clock_wrap.py`：用參考映像中的除法函式計算新商、舊商與 W，與整數除法交叉核對，接上既有的累計與 APP 換算模型；一般及 `-O` 通過。依賴同前篇，本地需有兩份固定映像與既有解碼器。不是連續 CPU、硬體計時或實際 ROM 安裝的證明。
