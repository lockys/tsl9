# V1.31 參考：0x6e0e2 之後是否影響模式保存框架？

接續 [入口參數的界限](v4160-mode-resident-restore-conditions.zh-TW.md)。只討論 `0x43986` 呼叫前分子為 `1600*u+800`、分母為 `1600`、`u` 為無號半字的情況。這不是對所有呼叫或裝置 ROM 的結論。

`0x6e0e2` 段選取索引 `1600 >> 8 = 6`。`0x6df48` 的 `18 23` 在 Xwchc 配置下是 byte load（標準 RV 解碼不同）；表基址 `0x6e95c`，參考映像 `+6` 的 byte 為 3。故位寬 11、左移量 21；正規化分母為 `0xc8000000`。兩個 16-bit 商位的修正項因分母低半字為零而為零，控制流依序取 `0x6df88 → 0x6df9c`、`0x6dfb8 → 0x6dfce`。`0x6dfd4` 執行 ret，回傳 `a1:a0 = 0:u`。

在上述成功讀取的靜態路徑，除取指外只有一次表讀，沒有 store、SP/s0 寫入或巢狀呼叫。因此算術 helper 本身不會改寫入口保存的 s0。不能據此消去呼叫者返回後 `0x4398a` 的物件寫入，或先前呼叫的記憶體副作用。下一個應核對的是該物件指標的來源與資料配置，而不是再展開除法的其他分支。

檢查器：`python analysis/check_v131_mode_timer_return.py <V1.31參考BIN>`。核對整個 carrier SHA-256、五段機碼、Xwchc 操作數與表值，窮舉 65,536 個 u；一般及 `-O` 均通過。這是按指令人工轉寫的算術投影，不是獨立 CPU 或實機測試。
