# 先前的大額請求之後，兩個初始化呼叫是否配置小物件？

接續[初始化中的第一筆大額請求](v4160-mode-timer-prior-init-allocation.zh-TW.md)。限其成功後繼續的 V1.31 候選路徑，並區分函式自身與間接回呼。

- `0x43c00` 呼叫 `0x4329a`。完整函式只有 LUI、SW、RET：將零寫到 `0x20003198` 就返回。沒有配置呼叫，也沒有寫 `0x20003194` 的小額起始游標。
- `0x43c04` 呼叫 `0x44022`。設定 `+8` 的 word 為零，或 `+56/+60` 任一回呼指標為零，都會返回而不執行本函式的配置。否則先執行 `+56` 的間接讀取回呼；正常返回後，比較其輸出的 word 與重新讀取的 `+8`。相等也不配置。
- 不等時，`0x44060` 在 Xwchc 解碼下讀取設定 `+12` 的無號半字到 a0，`a1=78`，`0x4406a/6e` 呼叫 `0x20000040`。這是**暫存區大小取決於實際設定**的呼叫，不是固定 16 bytes 的計時器節點。先前 `0x43cf0..0x43cf9` 對零值預設為 256；若該預設保持且確有配置，256 經對齊仍是 256，選大額游標。非零的自訂設定不能一概套用此判定。

因此，在預設 256 的條件下，兩個函式中已識別的直接行為不能證明小額起始標頭已被占用。此結論不涵蓋讀寫回呼內部或後續其他初始化呼叫，不能由此給實際計時器指定地址。後續應回到原 APP 的設定結構，核對 `+12` 是否明確賦值或只依賴初始清零；這可決定是否有理由採用 256，而非繼續假設。

驗證：離線反組譯兩個入口；Python `-IOB` 核對固定參考 SHA-256、六段機碼、半字載入操作數、配置呼叫目標與預設大小分類。沒有執行回呼、讀寫實機儲存或修改韌體。
