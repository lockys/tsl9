# 取消狀態從 b4d2 傳回佇列後，誰先使用 a0？

結論：這條 APP 路徑的佇列迴圈不以取消狀態分支。但「沒比較」不等於「丟棄」：若後續項目全空，a0 可以一直保留到主迴圈的下一個間接呼叫。

1. `12d8c` 呼叫 `14d2e`，把 `12d90` 留在 ra。派送器保存 ra；若到達 `14e84` 且 a5 等於 755，`14e88` 跳到 `1513c`，從 sp+12 還原 ra，`15144` 尾跳 `b402`。不是從 `15148` 接結果。
2. 若走到 `b4d0` 的取消呼叫並正常返回 `6`，且 `b4d2` 的 s1 為零，`b4d4..b4de` 還原 ra 等暫存器，不改 a0。正常堆疊下返回 `12d90`。這個 s1 是內層值；還原後的佇列索引不必等於零。
3. `12d90` 跳 `12cee`；索引加一後和 32 比較。`12c94` 用項目的半字判空。若剩下有非空項目，第一個非空項目在 `12ca2` 以 sp+8 覆寫 a0，再呼叫複製服務。兩個判斷都不是看 `6`。
4. 若本項為最後一項或後面全空，`12cf8..12d0c` 直接返回，未改 a0。由 `81a2` 呼叫時，`81a6` 寫 s0，`81a8` 跳 `8198`，載入 a5 後 `819c` 間接呼叫。到該呼叫前 a0 仍可等於 `6`；沒有看見 APP 用它選目標。該服務是否讀 a0 是獨立問題。

重現：以 SHA-256 為 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 的 decoded APP，檔案偏移 = PC − 0x8000。用 RV32C 從各指令起點反組譯：

| PC | 原始 little-endian bytes | 核對重點 |
|---|---|---|
| 14e84 | `1307302f638ae72a` | 比較 755 |
| 1513c | `22852244b24041016f60efab` | 還原 ra、尾跳 |
| b4d0 | `513395ecb24022449244024941018280` | s1=0 返回 |
| 12d8c | `ef10307ab9bf` | 呼叫後無條件跳轉 |
| 12cee | `850493070002e399f4f8` | 索引而非狀態 |
| 12c94 | `a9cf7330098083a7c9043146a28528008297` | 空項跳過；非空換 a0 |
| 12cf8 | `b640264496440649f259625ad25a425bb25b61618280` | 返回不動 a0 |
| 8198 | `832709008297efe05066efa0702b80c0c5bf` | 下一輪間接呼叫 |

以上是對指定返回鏈、正常載入與未受干擾的保存區所作的靜態結論，不證派送條件在裝置上成立，也不證間接服務採用任何特定 ABI。
