# 設定寫回後的延遲回呼 0x960e

`0x14366` 要求 `0x9124(0x960e,0,100,0)`，不是直接呼叫 `0x960e`。以下描述回呼真的被執行、存取成功且外部呼叫按預期返回的情形；不是實機紀錄。

1. `0x9614` 呼叫 `0x9410(3)`。若舊指標 `[0x2000becc]` 非零，先傳給槽 `0x40068`，再清 `0x2000becc`、`0x2000bec8`，呼叫 `0x93ee` 操作外設。接著以 `6*3=18` 尾呼叫槽 `0x40070`（假定 s0 維持）。舊指標為零則直接進入後段。不能把新請求失敗解釋為完全沒有狀態改變。
2. `0x961a` 先把返回值 P 存入 `0x2000becc`，再判斷 P 是否為零。零則返回。非零時依序寫半字 `(偏移,值)=(0,1165),(2,130),(6,1465),(4,0),(8,150),(10,0),(12,0)`，尾跳 `0x93aa`。18-byte 請求不等於 18 bytes 都由此回呼初始化；+14..17 未在這段寫入。
3. `0x93aa` 重新讀取設定指標 `[gp+84]`；其 +2 位元組和 `0x2000bec0` 的位元組 **同為零** 才直接返回。否則清兩個位元組 `0x2000bec2/0x2000bec1`、一個字 `0x2000bebc`，半字寫零到 `0x40000424`，讀 `0x40000400` 半字並將 bit 0 置一後寫回。這是指令所請求的操作，不能以此證明裝置已產生可聽或其他外部效果。

驗證：原 APP SHA 固定；`check_v4160_callback_960e.py` 解出六個 PC-relative 儲存與七個有序半字寫入，並固定大小計算與 MMIO 尾段機碼。不是從排程器開始的連續 CPU 模擬。
