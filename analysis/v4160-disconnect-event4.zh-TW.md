# 斷線清理沒有直接停止事件 4 的計時器，也沒有清掉待辦位元

**原 APP**（SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`）：在 `0x8c3e` 的斷線路徑，事件 opcode 不等於 6 或 handle 未匹配就返回；匹配時 `0x8c68` 將所選 handle 改為 `0xfffe`，不改該記錄的 task ID。後續只有 `0x8b6e(1)` 和 `0x13e0e(重新讀到的 handle,0)`。後者只清另一組相符記錄，沒有呼叫；前者要求設定廣播啟用 byte。沒有直接呼叫參考 SDK 的 `tmos_stop_task`（表項 10，停止計時器）或 `tmos_clear_event`（表項 8，清待辦事件）。兩者不可視為同一操作。

**廣播設定服務是否間接取消？** 在 V1.31 參考 carrier（SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`），`[0x40174]=0x6d834`。參數 `0x305` 減 `0x301` 得 4，跳表 `[0x6e910]=0x6d8aa`。以正常 stack、長度 1 和 Xwchc byte-load 解讀 `0x6d8b6` 時，新值為 1，取舊值並更新 `0x200035a8`。舊值非零即返回；舊值零時，只有狀態 word `[0x200035cc]` 等於 1，或低四位為 3、4 才到 `0x6d90a`。該處用 `[0x200035f5]` 的 task ID 和 **mask 1** 呼叫 `0x4354a`（表項 7）。這是發送另一個事件，不是停止 event 4。關閉廣播的另一條路徑不適用於這次輸入 1。

因此，若先前排程的事件 4 之後仍被交付，`0x8614` 按當時 task ID 選欄並重新讀 handle，而非保存斷線前的值。此處不能證明事件仍在佇列、實際交付，或參考 ROM 與設備相同。也不排除其他非同步清理。

核對：固定 carrier 身分、表項與 case 目標；解碼 `0x6d90a` 的 JAL 至 `0x4354a`；對 65536 個狀態樣本比對無號分支式。另重跑 `check_v4160_event4_params.py`，核對接收端的事件位與請求參數。
