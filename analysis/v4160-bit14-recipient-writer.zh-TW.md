# `0x2000324b` 的另一個寫入來源

接續[投遞呼叫點](v4160-bit14-poster-caller.zh-TW.md)。在 V1.31 參考映像中，`0x46592` 並不是這個 byte 唯一的寫入點。`0x455c2` 的第一個參數控制收件 task，第二個參數是另一個欄位。

* `0x455ce..0x455d0` 將 `a1` 存入 `s1`、`a0` 存入 `s2`。隨後以 `(0x20003248,0,32)` 呼叫 `0x2000039c`。若它正常返回並保留 `s0/s1/s2`，`0x455e6..0x455ea` 就將 `low8(入口 a0)` 寫到 `0x20003248+3`；`0x455f2` 則將 `low8(入口 a1)` 寫到不同位置 `0x200033b0`。這兩筆寫入都在下一次呼叫 `0x5336e` 之前。
* 上游 `0x49b92` 用 `(a1-1)&255` 分派，12 項跳表起於 `0x6e380`。低 byte 為 1、2、4、8、12 的五條路徑，各自設定 `a1`，不改 `a0`，就直接呼叫 `0x455c2`。例如選項 4 可以配收件 ID 3；選項 3 本身卻走 `0x49c64`，不是這五個呼叫點之一。
* 因此參考程式**能寫入 3**，條件是上游第一參數的低 byte 為 3，不能從選項、先前的 `0xff00` 或 APP 校準 task 的登記次序推得。尚需追 `0x49b92` 的呼叫者及至投遞時的寫入順序。這不是實機 ROM 身分、實際參數或事件已投遞的證據。

重現：對 SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22` 的 carrier，以 `PC-0x40000` 取檔案偏移。寫入指令原碼 `a3812701`、`2388973a`；跳表 12 個小端 word 依序為 `49bc8 49be8 49c64 49bfa 49c64 49c64 49c64 49c1c 49c64 49c64 49c64 49c40`（十六進位）。五個 JAL PC 為 `49bca 49bea 49bfc 49c1e 49c42`，目的地皆為 `455c2`。
