# v4.1.60：事件記錄索引的初始化順序

接續[索引寫入盤點](v4160-app-event-record-selector.zh-TW.md)。這裡重建原 APP 指令的呼叫順序，不把間接目標的行為當作已知。

- `0x927c`、`0x9280`、`0x9284` 依次呼叫 `0x154a6`、`0x17040`、`0x173a2`。若都回到各自續段，`0x928c` 在還原框架後尾跳 `0x17bf6`。
- `0x17c0a` 先透過 `[0x40048]` 傳入 `(gp+376, 0, 3)`。下個續段重新載入同一 slot，`0x17c1c` 再傳入 `(0x2000c8ac, 0, 115)`；目的位址按 `0x17c14` 的 AUIPC 基準解碼，不沿用其他初始化路徑的位址。第二呼叫以正常返回且保留 `s0=0x40000` 為前提。
- `0x17c2a` 透過 `[0x40080]` 傳入 `0x176f8`，也就是通往 `0x17780` 索引讀取的函式入口。隨後保存回傳低位元組至 `gp+379`。`0x17c38` 將另一個函式位址 `0x178f8` 交給 `0x90b0`。
- **之後** `0x17c40` 才呼叫 `0x1798a(1, 0)`。在正常轉入已核對分支時，`0x179e4` 直接把 `gp+376` 寫成零。`0x17c4a` 再尾跳 `0x17b92`。

因此，這條路徑先把索引讀取函式的位址交給間接目標，之後才做已驗證的直接寫零。較早的間接清零請求不能當作已完成的清零，也不能假定間接目標只儲存回呼、不會立即呼叫。此順序不證明首次實際讀取已初始化，也不證明有提早讀取；較早三個呼叫與其他入口仍未在此排除。

以原 BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 核對：Python `-O` 通過五個原始指令窗、七個 JAL 目標與三個 AUIPC/ADDI 位址；另反組譯交叉確認 `0x176f8` 入口。未連設備或改動原 BIN／正式來源。下一步辨識 `[0x40080]` 候選目標對回呼指標的使用方式，區分立即呼叫、延後排程及僅保存。
