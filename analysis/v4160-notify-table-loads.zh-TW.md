# 通知表的啟動來源：預設頁沒有 111、112、113 命中

[上一步](v4160-notify111-113-writes.zh-TW.md)只排除了 reset 清零後的空表。重新核對 APP `0x131c2` 載入流程，以下三次均經 `[0x4004c]` 要求複製 256 bytes，再讀目的頁末 byte。等於 `0x5a` 跳過對應 fallback；此檢查沒有驗證頁內的 key。

|通知表（reset 綁定）|呼叫 PC|來源運算元 → RAM|末 byte 不符時的 fallback|
|---|---|---|---|
|gp+96|0x13222|0x08077900 → 0x2000c494|0x12e86|
|gp+100|0x13282|0x08077700 → 0x2000c594|0x12f7a|
|gp+104|0x132b2|0x08077600 → 0x2000c694|0x13084|

各 fallback 先要求 `[0x40048]` 清零整頁，再設標記並寫入不同預設項。離線測試固定原 APP SHA-256，假設清零成功且 s0 保留頁基址，由原機碼逐指令重播填值，停在各自的儲存包裝尾跳之前。按 `0x167a6` 對第一表掃 127 對、對後兩表各掃索引 1..35 並檢查啟用位，三種通知在三份預設頁合計 **0 次命中**。第一表標記在 offset 255，不是被掃描的 key；第三表雖設了第 0 筆，迴圈從第 1 筆開始。

結論是逐表的：若這張表仍保有 fallback 結果且綁定未變，可排除它派發這三個通知。若末 byte 合格而保留載入內容、後續另有寫入或綁定改變，則仍未知；未取得裝置頁，亦未執行儲存包裝或 ROM 服務。重播：`python analysis/check_v4160_notify_defaults.py <decoded-bin>`（一般與 `-O` 均通過）。
