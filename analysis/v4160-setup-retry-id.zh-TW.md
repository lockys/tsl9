# 0x16f00 的重試送給哪一個任務？

原 APP `0x1706a` 經槽 `0x40080` 以 `0x16f00` 登記，返回低 byte 保存至 `gp+363`。在 V1.31 參考服務中，成功時將 handler 寫入舊計數 n 的表列並返回 n；滿表返回 255 而不建立該列。參見[登記順序](v4160-event4-task-id-order.zh-TW.md)。不從這段推定 n 為固定數字。

關鍵差異在於，失敗重試路徑**不重讀 `gp+363`**。參考 dispatcher 在 `0x40b5e` 重讀目前索引 i 至 a0，以它選取 `table[i]`，在 `0x40b7a` 呼叫該列 handler，a0 仍是 i。若它確實派發到此 handler 且選中遮罩 1，`0x16f7e` 先將入口 a0 保存到 s1。兩次設定任一返回非零，`0x16fb0` 把 s1 還原為第一個參數，呼叫 `[0x40058](i,1,48)`；V1.31 參考槽指向 `0x43728`。

因此，若穩定表中的已登記列 n 被派發，重試請求的任務也是 n；即便同一 handler 出現在另一列，從那列派發就會請求另一列的 ID。這不是由函式地址決定的，也不是對 gp 快取值的查找。須假設 setup 正常返回且保存 s1；不證定時器已建立、事件必再派發、設備 ROM 或實際 ID。

`python analysis/check_v4160_setup_retry_id.py` 固定 APP/參考映像與相關指令；解讀選列及保存/還原指令，注入成功索引範圍 0..254、兩條失敗路徑和異列控制。合成表不代表真實註冊容量。普通及 `-O` 皆通過。
