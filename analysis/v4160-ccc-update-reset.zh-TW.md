# 哪些 CCC 更新會改變下一次 TX 查詢？

原 APP `0x88be..0x88ca` 在 UUID 0x2902 分支尾跳 `[0x40144]`，a5=1。它傳入屬性指標，不是直接傳 gp+128。V1.31 參考服務 `0x4b4a4` 接受 offset 0、長度 2、沒有超出遮罩的值；從屬性 +12 取表指標，先讀再比。相等直接成功，否則尾跳 `0x4b46c`。只有該指標就是 TX 表且綁定與表穩定，以下才適用於 TX。

- 正常 handle 已存在：查找回傳第一筆。只寫其 +2 byte，後續相同 handle 的值未改。把值寫為 0 不會釋放 handle。
- 不存在：原查詢結果是 0，所以要求 0 直接成功，不占列。要求 1 才查找第一筆 `0xffff`；命中先寫半字 handle 再寫 +2 byte；無空列回 17。
- 原 APP `0x8faa..0x8fb8` 在 s0=0x40000 時，以 `(0xffff,gp+128)` 呼叫 `[0x40138]`。V1.31 `0x4cfd0` 此分支到 `0x4b33c`，依取樣筆數清全部列（handle=0xffff，值=0，+3 未寫）。相反地，服務的非萬用 handle 分支只清第一個命中；若有重複，原第二筆才成為新首筆。這不表示 APP 此初始化呼叫走了單筆分支。

`check_v4160_ccc_update_rows.py APP.bin V131-carrier.bin` 校驗兩份 SHA、APP 片段、四個槽及四個 Xwchc 寫指令，再對 0..3 列列舉 1640 組有效值更新模型。不是整段 CPU 執行，未證實裝機 ROM、屬性表綁定或實際兩次查詢之間發生更新。
