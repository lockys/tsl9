# 到期之後：下一輪掃描前缺哪些輸入？

承接 `v4160-due-next-scan.zh-TW.md` 的 128 個一次性計時器返回狀態。若排程器正常返回 APP 呼叫點的續址 `0x819e`，並非立即重入掃描：

1. `0x819e → 0x17002`。名義 gp=0x20004000。`0x17004` 與 `0x17020` 分別讀 `0x20004168`，測 bit 0、bit 1。任一次命中會先清該位，再呼叫 `0x16b0a(1 或 2)`；不能把第一次讀值當作第二次讀值。
2. `0x81a2 → 0x12c58`。逐筆讀 `0x2000c038 + 12*i` 的半字，i=0..31。全空則沒有子呼叫；遇非空記錄時，在 `0x12ca4` 經槽 `[0x4004c]` 間接呼叫，再依記錄內容分流。未證明這些子呼叫一定會改變任務 3 的事件。
3. 兩者都返回且保留迴圈暫存器時，`0x81a6` 把 `0xaaaa` 寫至 `0x40003000`；`0x81a8` 回到 `0x8198` 從 `0x20000000` **重新讀**下一次呼叫目標。這個直接寫入不是寫任務 3 的事件半字。

用原 APP 離線反組譯以上位置，並檢查計時器返回時的同一份稀疏 RAM，而非另設空佇列。128/128 例都缺旗標 byte、全部 32 筆首半字（64 bytes 均無資料）和排程入口槽的四個 bytes。一般 Python 與 -O 都得到 `APP INPUTS Counter({(None, 0, 32, None): 128})`（旗標、已知零列數、未知列數、槽）。這不是讀到零。即使 reset 的清零涵蓋旗標和記錄表，也還須證明後續寫入，不能用初值替代這裡的讀值。

因此可以定位第一個未知讀取，不能把服務呼叫視為無副作用，或把上一次「另從掃描入口開始」改稱連續派送。V1.31 為參考而非已確認的裝置 ROM；未執行實機或外設。
