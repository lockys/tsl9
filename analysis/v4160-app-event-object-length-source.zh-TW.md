# v4.1.60：事件物件長度的寫入來源

接續[周邊寫入欄位](v4160-app-event-dispatch-writer-fields.zh-TW.md)，本輪確認一條能更新物件 `+2` 的原 APP 路徑，不把它當成唯一寫入來源。

- `0x82a8` 依傳入索引組出 `0x2000c1b8 + 12*index`；索引 18 對應事件解碼器使用的物件 `0x2000c290`。當模式參數 `a0=0` 時，尾呼叫 `[0x4004c]` 的參數是 `(槽地址, 原 a2 指標, 12)`；非零模式的方向相反。
- `0x152ba..0x152c0` 傳入模式 0、索引 18 和來源 `s0`。若間接函式遵循候選 byte-copy 語意且正常完成，物件 `+2` 就取自來源記錄的第三個位元組。固定 12 bytes 是這次更新物件的長度，不是下游分派器用來構造資料的長度。
- `0x152cc` 在正常續段尾轉移至 `0xc6a8`。該解碼器以其傳入暫存器為物件指標；此處 `0x152c4` 放入的是 `s0`，不能因為前一步寫了第 18 槽，就認定這次尾轉移一定處理第 18 槽。由事件回呼經 `0xc776` 進入 `0xc6a8` 的路徑才明確傳入 `0x2000c290`。

Python `-O`：固定 APP SHA-256、64 bytes 指令窗、索引 18 的地址、兩個 JAL 目的與 13 組合成複製通過。這些案例不證明來源長度值的實際範圍，也未執行設備或間接 provider。下一步回溯 `0x152ba` 的 `s0`，先核對入口如何形成來源指標，再找上游寫入長度 byte 的位置。
