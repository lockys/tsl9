# v4.1.60：IRQ 39 的控制器設定早於外部線設定

直接核對 ID 2966 APP（基址 `0x8000`，SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`）。把三處指令放在一起看，才能區分「要求啟用」與「中斷已送達」。

- Reset `0x18704..0x1870c` 形成 `0x1888` 後 `csrs mstatus,t0`，包含 MIE（bit 3）及 MPIE（bit 7）。這是 OR，不是把整個 CSR 指定成 `0x1888`。接著 `0x1871c` 寫 `mtvec=0x803b`；表基址 `0x8038` 的第 39 個索引在 `0x80d4`，原始 word 為 `0x16fb6`。`0x18730` 跳到 APP 外，不能假設中間的 resident 保持這些值。
- 在 APP 初始化函式 `0x9250`，`0x9258` 呼叫 `0x9a42`。其尾段先在 `0x9ab6` 寫 byte `0x30` 到 `0xe000e427`，再在 `0x9abe` 寫 word `0x80` 到 `0xe000e104`。依候選 PFIC 配置，兩者指向同一通道：優先權 byte 索引 `0x27=39`，啟用 bank 1 的 bit 7 即 `32+7=39`。此前同址的 `0x2000`、`0x10` 是其他通道的獨立寫入。`0x9ac2` 設的是 CSR `0x800` 的遮罩，不是又一次寫 `mstatus`。
- 在先前呼叫均正常返回的路徑上，直到 `0x9280` 才呼叫 `0x17040` 設定[外部線 6、7](v4160-irq-line-setup.zh-TW.md)。因此可證 APP 寫控制器的順序，不能證這些位元持續有效、引腳曾有下降沿、或 CPU 曾進入處理程式。

重現：在原 BIN 以 `VA−0x8000` 取 `0x9250..0x9284`、`0x9a96..0x9ac6`、`0x18704..0x18720`（右端不含），用 RV32 小端反組譯並保留各段起始 VA；另讀檔案偏移 `0xd4` 的 LE32。以上未使用設備或修改韌體。
