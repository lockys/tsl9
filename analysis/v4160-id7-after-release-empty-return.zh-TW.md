# 任務 7：回收 A2 訊息後的第二次取件

接續 [原配置回收](v4160-id7-a2-release-block.zh-TW.md)。本機測試把釋放例程完成後的同一份合成資料 RAM 傳給下一段；不是重新建立空佇列。從 V1.31 參考常駐程式 `0x46674` 開始，以獨立、分離的模擬 handler stack 和返回標記重播，未串跑 `0x43200` 到這個起點的 wrapper 尾段。

1. `0x46674/676` 由 stack 保存的基址重新讀取目的 ID（本例 7），再呼叫 `0x2000028c`。佇列頭已是零。空路徑不是立即 ret：它呼叫 `0x439a8(7,0x8000)`。
2. 在這批配置中，計時器查找沒有匹配，`0x4358a` 清除任務 pending 半字的 bit 15。當前游標等於 7，`0x439f4` 把 `0x8000` 併入另一個半字 `0x200031dc`。`0x439a8` 最終回傳 6，但取件例程交回的是保存的訊息指標 0，不是 6。
3. `0x46682` 收到空指標並跳回檢查；`0x46610` 對原 handler 事件遮罩 XOR `0x8000` 後返回。本路徑原遮罩必有 bit 15，因此其他位元原樣保留。這不是把 RAM 裡的 pending 半字當作返回值。

| 案例 | handler 輸入 | 空取件前 pending | handler 返回 | 取件後 pending | 0x200031dc |
|---|---:|---:|---:|---:|---:|
| 承接回收後 RAM | 8000 | 0000 | 0000 | 0000 | 8000 |
| 分別改動兩個遮罩的控制 | 8005 | 8042 | 0005 | 0042 | 8000 |

表內數值為十六進位。一般 Python 與 `-O` 各通過 128 個承接案例及 128 個控制案例。假設 V1.31 映射、Xwchc、名義分離的堆疊、正常記憶體和無干擾。本次只發布報告，不代表目標設備或其他排程狀態；尚未把這個返回值帶入排程器返回後的指令。
