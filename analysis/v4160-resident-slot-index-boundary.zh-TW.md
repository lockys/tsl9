# v4.1.60：resident 表基址與 APP 索引路徑

接續[啟動搬移篩查](v4160-resident-slot-startup-copy.zh-TW.md)。以 SHA-256 固定 APP、V1.30、V1.31。這一輪只查有限形式：半字對齊的 `LUI reg,0x40` 起點、其後不到 36 bytes 且不跨首個解碼出的 JAL/JALR 或壓縮跳躍的區間，找同暫存器參與 ADD/C.ADD，或以 ADDI 0/C.MV 搬到 a0–a7 的候選。候選以暫存器編號比對，必須再查是否已被覆寫；不等同控制流分析。

- 兩份 resident 各有三個此類 LUI 起點，沒有符合的索引加法或搬入參數指令。原本就在參數暫存器的兩處亦已識別：一處以 `0x40000` 作位元 OR；另一處先加 `0x2b0`，將 `0x402b0` 作為已知啟動複製來源，不是表基址轉傳。
- APP 的 228 個 LUI 候選中有兩處符合加法編號模式；靜態核對都發現原暫存器已被覆寫。`0x2c2` 以 RAM `0x200041b8` 加上 `12 * index`；候選的 `0x2c6` 參數搬移傳的是該結果。`0x10250` 則以 `[gp+84]` 加上 `(index+2)*8`，不是直接以 LUI 建立的表基址。這不聲稱所有可能的 RAM 值均已知。
- 另核對 `0xf844` 確實是動態索引讀取，但基址由 `0xf83a/0xf83e` 建立為 APP `0x12ae8`，不以 `0x40000` 為基址。

Python `-O` 的三份映像篩查與 APP 位址、指令窗核對均通過。這些結果沒有解析 `0x400fc`／`0x4011c` 的實際上游指標：遠距基址傳遞、其他取址形式及實機 resident 仍未覆蓋。把該分支留在未解析依賴清單，不再把同一個有限搜尋擴大當作完成進度，也不判定它是否讀取 state `+244..255`。接下來回到 APP，從已驗證的 `0xf844` 取表指令追蹤表長、索引來源與已知用途。
