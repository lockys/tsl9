# Flash 程式化入口順序與 ABI 審查

最終 C11／C++17 程式化函式均為 **100 B／38 條靜態指令**，正常返回契約、六函式元件及五個已知內部迴圈位置通過獨立檢查。這沒有證明完整原始角色、逐指令中斷或硬體可用性。[English](readme.en.md)

原始版本為 ID2966 Runtime SHA-256 `0ee64183…32fb667`，程式化範圍 `18EF2..18F56`。先前已封存的94 B原生版本有37條指令。差額的確切原因是移除 `18F08`、`18F12` 的兩條4 B基底 LUI，再新增一條2 B的 `LI A5,0`：`100−8+2=94`，`38−2+1=37`。4 B的 A0對齊 ANDI只移動位置，沒有造成這6 B差額。

| 實際產物 | B／靜態指令 | 第一控制讀取／A0對齊／第一控制寫入的偏移 |
|---|---|---|
| 原始 Runtime | 100／38 | `+4 / +8 / +E` |
| 先前原生版本 | 94／37 | `+4 / +18 / +A` |
| 第一個固定A0診斷版本 | 94／37 | `+8 / +4 / +E`，對齊早於讀取 |
| 恢復基底讀取的診斷版本 | 102／39 | `+4 / +6 / +E`，超出2 B |
| 最終自然100 B版本 | 100／38 | `+4 / +6 / +E` |

最終版本恢復兩個原始位置的基底具體化，並將兩個初始輪詢的遮罩結果固定於A5。實際編譯資料顯示第二輪詢離開時的A5零值直接成為索引，沒有額外的 `LI A5,0`。因此相對先前94 B版本是 `94+8−2=100`。這是實際機器碼結果，沒有插入填充或改換編譯旗標來追尺寸。靜態指令數不代表迴圈執行步數；忙碌輪詢仍無原始逾時。

最終A0在第一控制讀取之前仍是輸入D；讀取完成後才對齊，且在第一控制寫入之前已對齊。第一診斷版本把對齊移到讀取之前，無法保留該讀取失敗前的A0觀察；它沒有被當成最終解法。前一94 B版本則直到兩個初始輪詢結束才對齊。`program.py` 以完整100 B模式、新讀取順序、原生目的暫存器集合、64組32位元來源／目的複製及正常輸出檢查最終版本；IR另核對8／4個靜態 volatile i32讀／寫點及固定暫存器橋接。

然而第一控制讀取及 RMW的暫存器仍不同：原始使用A5，最終使用A2。在第一次控制寫入前，原始A2仍是入口值、A5為新讀控制字 OR `0x10000`；最終A2是該RMW結果、A5仍為入口值。初始輪詢雖都以A5處理狀態，最終A2仍保留RMW值，而原始A2直到256計數設定前保持入口值。正常返回時A0／A1／A2／A3／A4／A5／A6仍符合原始契約；這不能擴大成整段不返回、存取失敗或非同步暫存器前綴等價。

實際原始691區段 carrier 的程式化區段有五個內部符號位置 `+10 / +1A / +28 / +38 / +52`；最終原生分支與複製迴圈保留這些數值位置。七個相關RELA包含五個自身分支與兩個外部入口呼叫 `9C34`、`197D8`。此有限集合沒有外部內部位址RELA，但沒有排除計算式間接跳入。

即使長度和指令數相同，完整指令邊界也沒有相同：原始 `+8` 是ANDI入口，最終ANDI從 `+6` 開始，`+8` 落在其中；新邊界是 `+A`。原始LUI遮罩與ANDI順序交換，其他 scratch用途也有差異。原始內部符號名稱、全域入口別名、`$d`／`$x`對應等metadata並不會因尺寸相同而自動保留。100 B只關閉先前6 B未佔用的函式儲存長度問題，沒有完成整份 carrier整合或確認所有原始角色。

每種語言的純程式化檢查器拒絕 **12個實際機器碼反例**與 **3個未重新編譯的IR文字反例**。其中兩個反例仍是100 B，但分別把對齊移到第一讀取之前或第一寫入之後，直接證明只檢查尺寸不足。另五個函式沿用不可變的既有完整模式。審查實際六物件、IR、原始入口位置的元件ELF與JAL修補；沒有執行 RV32、模擬、連網、操作硬體或產生BIN。

`python replay.py --check` 只讀重播最終兩種語言產物及正式收據。`--context-json` 可提供 `project_root`、`prior_build`、`firmware`、`source_dir`、`parser`、依語言指定的 `build_roots`；只改輸入位置及歷史路徑標籤，不放寬來源或機器碼契約。`variants.json`、`original-roles.json`是保留的實際診斷／原始metadata觀察；診斷產物仍在時會重新核對其位元組。完整映像、未知內部入口、實體晶片、Flash幾何、寫入成功與OTA可用性仍未確認。
