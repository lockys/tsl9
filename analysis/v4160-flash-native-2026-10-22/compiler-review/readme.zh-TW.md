# Flash 原生 C／C++ 編譯產物獨立審查

六個函式的**正常返回暫存器契約與元件尺寸均通過**，範圍僅限實際保留的 C11／C++17 物件、LLVM IR 與元件 ELF。沒有把元件當成完整韌體；沒有執行 RV32、模擬 CPU、操作裝置、連網或產生 BIN。[English](readme.en.md)

`review-c.json`、`review-cpp.json` 記錄實際建置路徑、來源與工具雜湊、指令列、日誌、六函式全部解碼列及檢查結果。來源契約綁定同案 `source/seal.json`，沒有修改原始封存證據或產品程式。審查器重新解析實際 ELF，而非信任建置摘要的通過欄位。

| 原始入口 | 原始 B | 實際 C／C++ B | 正常本體寫入暫存器 | 與原始完整位元組相同 |
|---|---:|---:|---|---|
| `9C0A` | 64 | 64 | RA、SP、S0、S1、A0、A1，另含被呼叫者 | 否 |
| `18E90` | 8 | 8 | A5 | 是 |
| `18E98` | 30 | 30 | A3、A4、A5 | 否，常數載入順序改變 |
| `18EB6` | 14 | 14 | A3、A4、A5 | 是 |
| `18EC4` | 46 | 46 | A0、A3、A4、A5 | 否 |
| `18EF2` | 100 | 94 | A0、A2、A3、A4、A5、A6 | 否 |

實際編譯設定為 RV32IMAC_Zicsr／ILP32、`-Oz`、關閉 machine outliner 與 relaxation，並逐函式限制可分配暫存器。審查同時核對實際指令的目的暫存器，沒有把 `-ffixed-xN` 旗標當成保存證明。各 helper 沒有堆疊、隱藏呼叫、RA 寫入或額外配置資料；程式化函式不寫 A1，A6 的最後定義是來源的最後一次字讀取。

`9C0A` 實際框架是 32 B，來源 A1 儲存與新讀取都位於 `SP+12`，RA／S0／S1 的新恢復槽為 28／24／20。之前 64 B 試編譯曾使用 `SP+16`，已作為具體問題回報，修正後才承認正常契約。五個 JAL 在實際元件 ELF 中分別解析至原始五個入口；CSR800 在呼叫鏈前清除136，之後設定136，沒有保存／恢復先前 CSR 值。

上鎖後正常 A0 是向下對齊256的目的位址，A1 是程式化前從框架新讀取的來源，A2=256、A3=`0x8000`、A4=`0x40022000`，A5 是最後上鎖的新控制字 OR `0x8000`，A6 是最後來源字。程式化函式的正常 A3=`0xFFFEFFFF`、A4 為最後新讀控制字 AND 此遮罩、A5 為基底；A1 不變。審查全部原生指令模式與固定暫存器輸出 IR，並核對所有 volatile 存取均為32位元。

程式化的原生迴圈為零起始、加4、比較256，共64組來源 LW32／目的 SW32，資料偏移0至252；每字後仍有 bit1 輪詢。初始 bit0、初始 bit1、最後 bit0 輪詢及新讀控制值的設定／清除順序都保留。每種語言另有 **15個實際機器碼位元組反例**及 **3個未重新編譯的 IR 文字反例**，涵蓋錯誤來源槽、CSR、資料寬度、步進、分支、暫存器與 volatile；不能把後者說成實際 C 變異編譯。

元件 ELF 的六個獨立可執行區段均在原始入口位置；沒有 UND、殘留重定位或額外配置區段。審查從物件逐位元組重算五個 JAL 修補後的預期資料，再與實際連結資料比較。這只證明六函式元件的正常位置與契約。**94 B 不代表原始100 B的其餘6 B已被允許使用或補齊**；尚未完成完整 carrier、原始內部入口、別名、重定位及全部儲存範圍整合。

以下差異仍明確存在：原始保存順序為 S0、S1、RA、A1；編譯順序為 RA、S0、S1、A1。程式化對齊 A0 的指令移到兩個初始輪詢之後，原始版本在第一個控制寫入前已對齊。因此沒有證明逐指令中斷、框架前綴、存取失敗或不返回時的實體暫存器前綴等價。正常契約以有效框架、存取完成、輪詢終止及無未建模的非同步干擾為條件；HOST 通過不能消除這些限制。硬體成功、晶片與 Flash 容量、可復原性及 OTA 可用性仍未確認。

離線重播：`python replay.py --check`。它不呼叫編譯器或 disassembler；若原 Windows 工具仍存在，會再次比對工具位元組，否則使用已封存的實際工具觀察值。報告與所指的建置產物必須一併保留。

若封裝後目錄改名，使用 `python replay.py --check --context-json <本機對應檔>`；對應檔可指定 `project_root`、`parser_path`、`source_dir`、`firmware_path`、依 `c`／`cpp` 指定的 `build_roots`／`linked_elfs`。這只重新定位輸入，並在記憶體內正規化歷史路徑標籤，不改寫封存報告。新編譯工具可透過 API 的 `observed_tools` 傳入「實際工具路徑 → before_sha256／after_sha256」；兩者必須相同，檔案存在時還會重新計算雜湊。原始韌體、解析器、三個核心來源及所有機器碼契約仍有相同嚴格檢查。`context-check.json` 記錄兩種語言的預設／明確路徑結果一致，另拒絕六個工具漂移、錯誤解析器與錯誤韌體反例。
