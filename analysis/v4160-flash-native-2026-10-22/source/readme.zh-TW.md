# V4.1.60 Flash 原始碼與暫存器契約

本報告只針對 ID2966 原始 Runtime（SHA-256 `0ee64183…32fb667`，載入基底 `0x8000`）。沒有執行韌體、模擬 CPU、操作裝置、連網或產生 BIN。[English](readme.en.md)

`python inspect.py --check` 可離線重播。只有重新擷取反組譯時才需要已釘選的 Windows radare2；一般重播使用保留的 `r2-source.json`，逐列核對實際原始位元組及獨立解碼結果。

| 原始入口 | 長度 | 原始用途 | 本體實際寫入的 GPR |
|---|---:|---|---|
| `9C0A` | 64 B | 四分之一頁包裝流程 | RA、SP、S0、S1、A0、A1，另加被呼叫者的變更 |
| `18E90` | 8 B | 32 位元狀態寫入 | A5 |
| `18E98` | 30 B | 四次金鑰寫入 | A3、A4、A5 |
| `18EB6` | 14 B | 新讀取控制值後設定 bit15 | A3、A4、A5 |
| `18EC4` | 46 B | 對齊、控制、位址及忙碌輪詢 | A0、A3、A4、A5 |
| `18EF2` | 100 B | 64 次 32 位元資料寫入與輪詢 | A0、A2、A3、A4、A5、A6 |

六個區段共 **262 B／99 條指令**。完整 691 區段 carrier 的獨立區段、STT_FUNC 符號、尺寸與原始資料均吻合；來源不是由舊版模型位址平移推測。`source-proof.json` 包含全部原始指令、位元組、解碼欄位與 20 個實際原始位元組變異。變異在韌體雜湊檢查之前由語意契約拒絕，涵蓋錯誤 CSR、堆疊槽、呼叫目標、金鑰、忙碌位元、資料寬度、來源暫存器、步進、迴圈及回傳。

`9C0A` 配置 32 B 堆疊框架，依序儲存 S0 到 `SP+24`、S1 到 `SP+20`、RA 到 `SP+28`、來源 A1 到 `SP+12`。`9C1A` 清除 CSR `0x800` 的遮罩 `136`，呼叫解鎖、寫入狀態 `49`、擦除、程式化、上鎖，`9C3C` 再設定同一遮罩。它沒有儲存並還原原本的 CSR 值。程式化前 `9C30` 會重新從 `SP+12` 讀取 A1；返回前也重新讀取三個保存槽。僅以 C 區域變數持有來源指標，無法自行證明這些可觀察讀取等價。

`18EF2` 的 A2 不是傳入長度。原始 `18F16` 設定 256；第二個輪詢的遮罩結果 A5 在離開時是零，成為資料索引。`18F1E` 讀取來源字，`18F26` 寫入目的字，`18F30` 是 **2 B 的 C.ADDI**，每次加 4，`18F32` 在 256 結束。因此正常完成時有 64 組讀寫，偏移 0 至 252。來源與目的位址是 RV32 無號加法；實體映射、對齊例外及可存取記憶體仍未確認。

完整輸入、順序與正常返回的暫存器值見 `contracts.json`。特別是包裝流程返回的 A0 是目的位址向下對齊 256，**不是成功碼 0**。A1 是程式化前新讀取的來源指標，A2=256、A3=`0x8000`、A4=`0x40022000`，A5 是最後上鎖前新讀取的控制值 OR `0x8000`，A6 保留最後一次來源字讀取結果。一般 C 呼叫慣例或 HOST callback 通過不代表這些原始暫存器值已被保留；必須另查實際編譯的原生指令。

`9D00` 的已保留呼叫點後先讀取 S0/S5，再覆寫 A5/A4/A3/A2；這個有限範圍沒有使用它們的返回殘值。此觀察不延伸到其他直接呼叫者或未知的計算跳轉。先前 OTA 路徑、resident callback 與 Flash 鏈的三份封存證據均逐一核對成員雜湊並重用，沒有重跑歷史整條流程。

原始輪詢沒有逾時或錯誤回傳；任何一個忙碌位元永遠不清除時，後續資料、上鎖、CSR 設定及返回都不發生。HOST 測試若用預算中止，必須標示未知／未返回，保留已觀察到的前綴，不能宣稱原始韌體會逾時返回。所有結論以正常控制流程及已完成的存取為條件。尚未證明逐指令中斷行為、ROM ABI、實體晶片、Flash 幾何、硬體寫入成功、時序、復原性或 OTA 可用性。

後續原生編譯必須分別驗證 64／8／30／14／46／100 B 尺寸、每函式實際 GPR 寫入集合、32 位元新讀寫及輪詢順序、五個 JAL、框架與 CSR。不能把額外空間或暫存器視為可任意使用；整合前還須核對區段、符號、別名、重定位與內部入口。
