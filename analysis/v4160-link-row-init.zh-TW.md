# 三列連線 handle 的啟動初值

原 APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。初始化路徑在 `0x8fd8` 直接呼叫 `0x12506`。三筆空列不是由全零 RAM 自然形成，而是稍後由 APP 明確寫入 `0xfffe`。

| 指令位置 | 對列的操作 |
|---|---|
| `0x1252a..0x1253a` | s1 取基址 `B=0x2000bfec`，請求 `[0x40048](B,0,36)`，涵蓋三筆 12-byte 記錄。 |
| `0x12540..42` | s3 置 −2，先存半字至 **s2+6**；這不屬於三列的 handle。 |
| `0x125e6..0x125f2` | 對 B+0、+12、+24 分別寫 byte `0x80`。 |
| `0x125fa / 0x125fe / 0x12602` | 對 B+2、+14、+26 分別寫 s3 低半字，即 `0xfffe`；目的為 `0x2000bfee / 0x2000bffa / 0x2000c006`。 |

這些半字寫入不是填零服務的副作用。若前面的呼叫正常返回並保持 s1、s3，三條 store 成功且沒有干擾，第三條 store 後三列皆符合 `0x10d9a` 的空列判定；若首次建立事件到來時仍保持此狀態，會先選第 0 列。位址欄位是否全零則另需填零服務成功且後續無改寫。

驗證：核對原 BIN 身分、解碼 `0x8fd8` 的 JAL 目的地、以 AUIPC/ADDI 重算 B，並逐條解出三個 SB、三個 SH 的來源、基底與位移。`0x12606` 起尚有間接呼叫，本文沒有把初始化瞬間當成首次事件送達的實機快照。
