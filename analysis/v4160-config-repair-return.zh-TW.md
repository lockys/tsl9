# 第一個設定檢查失敗後，如何回到下一個區塊

接續 [四個 ASCII byte 的檢查](v4160-init-first-config-guard.zh-TW.md)。以下是 v4.1.60 原 APP 靜態指令；slot 的填零與複製語意僅在相符常駐程式、正常返回、保存所需暫存器且記憶體存取成功時成立。

1. `0x13204` 呼叫 `0x1316a`，返回位址是 `0x13208`。令 D=`0x2000c29c`。先向 `[0x40048]` 請求 `(D,0,112)`，再由 APP 自己依序寫 `U16[D+2]=0x0fff`、`U8[D+4]=1`、`U16[D+8]=0x0101`。接著重新讀 `Q=U32[gp+84]`，向 `[0x4004c]` 請求 `(Q+12,0x1a69c,4)`。**Q 是間接讀取，不能只因剛填了 D 就當 Q=D**；也不推定四個來源 byte 的業務意義。
2. `0x131be` 是不寫 ra 的尾跳，不會直接回到下一個設定。它到 `0x13138`，後者另外讀一次 `[0x4004c]`、配置 272-byte 堆疊框，請求複製 112 bytes 從 D 到框底，再以 `(0x08077a00,框底)` 呼叫 `0x9c0a`。
3. `0x9c1a` 對自訂 CSR `0x800` 清 mask `0x88`，其間有五個直接呼叫，`0x9c3c` 再設同一 mask。這不是讀回舊值，也不是 `mstatus`。其中 `0x18ef2` 的頁面迴圈界限是 256，不是前述 112；不能從該次複製推定整頁內容或實際寫入成功。輪詢未結束時，亦不能假定已執行後面的設位和返回。
4. 正常返回且堆疊保存有效時，`0x13162..0x13168` 還原 ra，回到 `0x13208`。成功檢查的路徑不走上述修復，直接在此會合。這裡重新讀 slot，請求 `(0x2000c494,0x08077900,256)`；之後檢查 `+255` 是否為 `0x5a`，不是重驗前一區塊。

核對原 APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`。以 RV32 反組譯並從位元欄位另核對 8 個 JAL 的目標及 link register、4 組 PC-relative 位址、112/256 兩個長度和兩條 CSR 指令；一般及 `-O` 皆通過，前一階段的 1024 個條件案例亦通過。無設備操作或實際頁面資料。
