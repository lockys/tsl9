# v4.1.60：物件 +7/+8 如何進入周邊寫入

接續[分派欄位依賴](v4160-app-event-dispatch-field-dependencies.zh-TW.md)，只追 `+11` 標籤為零、間接提供者正常返回的分支。

- `0x12a4e` 的複製目的為 `sp+23`，來源為 `物件+3`，長度取物件 `+2`。`0x12a54` 組出 `sp+12` 作為 `0x18ca4` 的輸入。假設提供者按參數逐 byte 複製、來源與目的不重疊且 SP 不變，複製區起點是 writer 輸入 `+11`；物件 `+7/+8` 分別對應 writer 輸入 `+15/+16`。
- 有選中 bank 時，`0x18ca4` 下游將輸入 `+15..+18` 組成小端 32-bit word，寫至 `port+396`。因此長度至少為 5 時，物件 `+7` 可成為該 word 的最低 byte；長度至少 6 時，`+8` 可成為次低 byte。短複製不會供應未覆蓋的 byte，本輪不假定那些 byte 為零。沒有選中 bank 時不走這筆寫入。
- 這確認的是 APP 資料流，不是寄存器的硬體用途、真實 provider 綁定、實機可達性或 `+11` 非零分支。

Python `-O`：固定原 APP SHA-256，使用既有五段原指令解碼，32 組合成案例通過（三個 bank 與無 bank、四種長度、兩組欄位值）。案例先注入合成複製結果，再核對 writer 的有序寫入紀錄；未執行真實複製 provider 或 MMIO。下一步回查 `0x2000c290` 的初始化和 `+2` 長度來源，判斷哪些欄位傳遞可由靜態證據支持。
