# 誰提供 bit 14 的目的 task ID？

接續[目的 ID 寫入點](v4160-bit14-recipient-writer.zh-TW.md)。在 V1.31 參考檔以半字對齊掃描 JAL/C.J/C.JAL，再核對相鄰指令，找到四個直接尾跳 `0x49b92` 的位置。四者都從 RAM 重新載入 `a0`，不是把呼叫者傳入的 `a0` 原樣交給設定函式。

| 尾跳 PC | 第一參數（目的 ID） | 第二參數（選項） |
|---|---|---|
| `0x6ab36` | `U8[0x200035f5]` | `U8[0x200035f4]` |
| `0x6ade8` | `U8[0x20002fb0]` | 8 |
| `0x6ceb2` | `U8[0x200035f5]` | 2 |
| `0x6d566` | `U8[0x200035f5]` | `U8[0x200035f4]` |

**與原 APP 的兩個連結。** `0x8872..0x8884` 經槽 `0x401a4`，候選值 `0x6d506`；`0x1236a..0x12382` 經槽 `0x401b0`，候選值 `0x6ad8e`。這兩個入口先把收到的 `a0` 低 byte 分別寫到 `0x200033b1/b2`，不是寫到目的 ID。前者在 `[0x200035cc]` word 非零時不走尾跳，後者在 `[0x200035ab]` byte 非零時不走尾跳。間接呼叫成立仍依賴實際槽綁定與各前置步驟正常完成。

**三條路徑共用的 ID 來源。** `0x43d48` 將 `0x200035f5` 初始化為 255。`0x6ab74`、`0x6cf0e`、`0x6d5b2` 各呼叫登記函式 `0x43c4e`，下一條指令一律是 `sb a0,1525(s1)`，在此處已建立且保留 `s1=0x20003000` 時寫回該 ID。它們登記的是另一個 handler，不是 `0x1995c`。若[第一個 APP 登記](v4160-first-app-registration-order.zh-TW.md)已佔用 ID 3，計數沒有重設或回捲，且角色登記在後，便不能從那次後續成功登記得到 3。這不是所有 writer 或所有時序的證明；第四條路徑的 `0x20002fb0` 仍須獨立追查。

重現索引：APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`（基址 `0x8000`）；參考檔 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`（基址 `0x40000`）。依表序四個 LBU PC 為 `6ab2a/6adc8/6cea6/6d548`，立即數 `1525/-80/1525/1525`。四個 JAL 的 rd 皆為 x0；三個登記 JAL 的 rd 皆為 x1，後接相同 store `a38aa45e`。本報告未驗證實機或窮盡間接入口。
