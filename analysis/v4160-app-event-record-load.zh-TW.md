# v4.1.60：APP 事件記錄的初始化載入與 fallback

接續[reset 指標來源](v4160-app-event-record-reset.zh-TW.md)，從原 BIN 重核[既有初始化盤點](main-initializers-2026-10-24/README.md)中 `0x2000c694` 的載入，並串接[事件參數資料流](v4160-app-event-record-byte.zh-TW.md)。以下是 APP 執行位址。

- `0x132b2` 透過 `[0x4004c]` 傳入 `(0x2000c694, 0x08077600, 256)`。按候選 copy 的參數方向，前者為目的、後者為來源，與 `0x1306c` 以同一 RAM 區域為來源的方向相反。原 APP BIN 不提供 `0x08077600` 的內容，且這不是實機 provider 已安裝或執行的證據。
- 返回後 `0x132b8` 讀 `0x2000c793`（基址 +255）；等於 `0x5a` 則跳過 fallback，否則 `0x132c4` 呼叫 `0x13084`。這個分支只查一個 byte，不驗整塊記錄內容。
- `0x13084` 先透過 `[0x40048]` 呼叫 `(0x2000c694, 0, 256)`。若該呼叫正常返回且保留 `s0`，後續 APP 本地指令寫 `base+255=0x5a`、`base+0` 的 word 為 `0x00ff0800 | (old & 0x200)`、`base+4` 的 halfword 為 `0x60ff`，以及 `base+6=20`；最後尾跳 `0x13052`。因此 **記錄 0 的第七 byte** 有一個直接的 APP 寫入者 `0x130c8`，不必用假定的 fill 效果推導這個 byte。

若事件處理之後確實選到記錄 0、以正常 copy 讀到該值且走到 `0x17832`，`a2` 的數值為 `800*(1+(20>>2))=4800`。但 fallback 從其間接呼叫返回後保留的 word bit 9 會決定 `record[1]` bit 1；若 `[0x40048]` 確實清零，該 bit 為 0，單靠這份預設記錄就**不會**走到 `0x17832`。這不是已觀察的呼叫參數或物理單位。

以既有 SHA-256 固定 APP BIN；Python `-O` 核對兩個原指令窗、位址與兩個轉移目標，並檢查 256 個 marker 值與兩種 fallback bit 9 合成情況，全部通過。未改 BIN、正式來源或既有本機變更。下一步區分正常載入與後續 APP 更新，確認是否有其他直接寫入記錄 0 的程式路徑。
