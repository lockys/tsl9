# 第十二個函式的整合邊界

[English](readme.en.md)

這份證據處理原始 `0x9B8E..0x9C0A` 頁面回覆函式的入口角色，尚未完成
第十二個函式的完整映像整合。既有十一函式映像及其封存證據保持原樣。

來向 `0x9DF4` 的指令已更正為會設定 `RA=0x9DF6` 的 `C.JAL` 呼叫；
不能只依 R_RISCV_RVC_JUMP 重定位種類判斷是否更新連結。詳見
[補充更正](../entry-call-correction/README.md)，舊來源封存的尾端路徑文字已被取代。

`inspect-owner.py` 讀取先前已驗證的完整部分連結物件，核對原始 124 bytes、
公開 NOTYPE／size 0 入口、區域入口、來自 `9C4A + 426` 的壓縮跳轉，
以及原本的內部分支與 TX JAL。`owner.json` 保存這次實際檢查結果。

`probe-boundary.py` 已在 C、C++ 各自實際編譯並部分連結兩個物件：
保留原入口的零位元組區段邊界，以及新 C/C++ 編譯並明確排序的函式。
新函式以連結腳本放入原始區段，實測沒有新增邊界位元組或填補。
公開入口仍是 NOTYPE／size 0，區域入口仍是 LOCAL／size 0，而可讀
C 函式是另一個真實 FUNC／size 124。沒有建立數值 ABS 入口別名。

實際結果也核對唯一外部入口重定位的原始區域角色、唯一 TX JAL，以及
其他原始承載區段的全部內容、配置屬性與外部重定位的完整角色及重數。
`probe-c.json`、`probe-cpp.json` 是選定的工作區收據封存；它們記錄實際
Windows 編譯與連結，不代表其他平台、完整映像或硬體已驗證。

## 重做這項局部驗證

先使用新元件的原生驗證器產生新的 C/C++ 物件。再指定其中一個語言目錄：

```sh
python analysis/v4160-ota-page-reply-2026-10-22/integration-plan/probe-boundary.py \
  --project-root . --tool-dir /path/to/pinned/llvm/bin \
  --native-folder experiments/tsl9-v4160-ota-page-reply/build/NEW/c --mode c
```

工具會先唯讀重播指定原生元件的完整來源、編譯及產物收據，才建立新的
承載物件與局部連結結果。輸出放在這個證據目錄下全新的 `build/` 子目錄。
不執行或模擬 RV32，不讀取原始 BIN 作生成來源，也不接觸硬體。

## 後續必要條件與新增功能候選

完整整合仍須重新證明所有 691 個配置區段、保留內容、符號、重定位、
固定地址、載入權限及輸出映像，不能把這個兩物件檢查當成完整證據。
原硬體、實際 ROM／BOOT、SP 與暫存器保存契約及 BLE OTA 仍未證實。

這個函式沒有自行檢查頁碼上限，標頭只輸出低 16 位，來源位址計算卻使用
完整 32 位索引。值得評估的新增功能是「更新前的離線頁面範圍與版本適用性
檢查」，先在主機工具阻止不明映像及超出已證實範圍的索引。這是候選提案，
尚未加入硬體韌體；加入裝置端檢查會改變程式大小與既有行為，必須另外
驗證呼叫端、記憶體配置及更新器相容性。目前不宣稱可燒錄。
