# v4.1.60 TX：從接納到收尾

以下的「事件 1、2」是遮罩 `0x0001`、`0x0002`。APP 可證它以哪些參數呼叫服務槽，不能僅由呼叫證明事件已派送。表中各列以服務正常返回、選擇同一 bank、所需暫存器有效為前提，不假設不同事件之間的 RAM 不變。

|階段|原 APP 可直接核對的轉移|不能由此推出|
|---|---|---|
|[接納與組框](v4160-dequeue-tx-reentry.zh-TW.md)|入口長度上限 1039。依序比對兩個 handle，排除 `0xfffe`；匹配後查詢恰回 1 才選其 bank。組框正常完成後寫總長、清游標，請求事件 1。|查詢內容、事件已入列或已傳送。|
|[事件 1：選片](v4160-tx-bit0-to-copy.zh-TW.md)|從當下 task ID 選 bank；CCC 查詢恰回 1 且剩餘量按有號半字解讀為正，才寫片段長度、設重試計數 10、請求事件 2。否則只清總長。|請求事件 2 不等於已複製片段。|
|[事件 2：取片與通知](v4160-tx-notification-result.zh-TW.md)|先查重試計數，不查總長；零則清總長，非零則請求配置。配置成功才重讀游標與片段長度並請求複製。此處 CCC 看最低位，不是前兩階段的「恰回 1」。|事件本身沒有指定是哪一個 frame，也不保證配置或通知成功。|
|通知失敗或未能發出|配置失敗、CCC 最低位為零或通知返回非零，走重新讀計數、減一及請求延遲事件 2 的路徑。從 1 減到 0 這次仍請求。|不保證延遲事件獲派，也不保證下次仍讀同一片段。|
|[通知成功與收尾](v4160-tx-final-fragment.zh-TW.md)|成功返回後重讀游標、片段長度，更新游標並請求事件 1。若正好抵達末端且值未變，後續事件 1 只清總長；游標、片段長度與重試計數並未一起清除。|總長為零不是事件 2 的停止條件；通知成功不是對端收件證明。|

**參考 ROM 才支持的部分：**[兩版候選的設位服務](v4160-dequeue-tx-event-leaf.zh-TW.md)對合法 task ID 將遮罩 OR 到 pending 半字，不同步呼叫 handler。[V1.31 候選的延遲重試](v4160-tx-old-timer-vs-post.zh-TW.md)另按 `(task, mask)` 查計時節點。立即設位和更新期限不是同一操作；這沒有證明裝置採用該 ROM、曾有舊節點或發生重送。

**重現範圍：**以 SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667` 的原 BIN 重跑上述接納、選片、通知與收尾四份報告內的 Python 檢查，一般與 `-O` 均通過。這是四段指令與局部條件的交叉整理，不是連續 CPU 執行，也不增加已重建的位元組數。
