# `0x4398a` 的寫入目的地從哪來？

接續[算術函式返回](v4160-mode-resident-timer-return.zh-TW.md)。此頁分析 V1.31 參考 carrier（SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`），不是設備 ROM 鑑定。

在候選 RAM 程式已按參考布局複製且採 Xwchc 解碼時，`0x20000314`（carrier 位址 `0x40584`）從 `0x200031e8` 讀取串列首指標。對每個非零節點，先比 `uint16(node+2)` 與第二參數；相等才比 `uint8(node+0)` 與第一參數。不符則讀 `word(node+12)` 繼續；匹配則回傳目前節點，遇零則回傳零。讀取寬度是機碼層級的描述，並不宣稱 C 型別或串列必定終止。

`0x43962` 將查找結果放入 s0；為零時不執行 `0x4398a`。非零且算術 helper 走前述已核對路徑時，該指令將一個 word 寫至 `node+4`。固定在 RAM 的是**首指標的儲存位置**，不是節點物件本身。

在 `0x434c2` 和 `0x43850` 找到兩個空串列分支把當時的 a0 放入首指標；`0x43b42` 則寫零。前兩段也寫 `node+12` 及 `node+4`，支持節點布局，但這些片段沒有給出配置區間。這不是全域 writer 清單。就本次證據，不能證明 node+4 與保存 s0 的框架位置分離，也沒有觀察到實際重疊。

驗證：離線反組譯並以 Python `-IOB` 核對參考檔雜湊、六段機碼及兩條 Xwchc 載入的欄位；未接設備、未改原 BIN。後續優先往兩個首節點建立點上游確認 a0 的配置來源，而非繼續展開除法。
