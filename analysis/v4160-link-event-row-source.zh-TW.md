# 連線列的六個位元組來自哪個事件？

原 v4.1.60 APP SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`，載入基址 0x8000。0x1a548 相對跳表的項 5 指向 0x1184c，項 13 指向 0x11570。兩者即使報告同一裝置，也不是同一次欄位讀取。

- 項 5：間接呼叫返回後，0x11860 讀取 `event[1]`；非零跳到 0x11924，略過本次填列。為零時 0x10d9a 按順序讀取三個 handle 半字，第一個等於 0xfffe 的列回傳索引 0、1 或 2；都不符回傳 3。0x1187c 只允許索引 ≤2 進入填列段。
- `R = 0x2000bfec + 12*index`。0x11878 從 `event+10` 載入半字；0x118ac 先把它存入 `R+2`。0x118ba 再透過 `[0x4004c]` 要求複製 `(目的 R+4, 來源 event+4, 長度 6)`。三個目的起點為 0x2000bff0、0x2000bffc、0x2000c008。因此 handle 寫入與六位元組複製不是單一原子更新。
- RV32 編譯期檢查：SDK `gapEstLinkReqEvent_t` 的 `hdr.status`、`devAddr[6]`、`connectionHandle` 偏移為 1、4、10，opcode 為 5；探索事件 `gapDeviceInfoEvent_t.addr` 偏移為 5，opcode 為 13。對照前一份連線列報告，通知/指示處理按 handle 選現存列，並非直接重讀探索事件。

驗證：原 BIN 雜湊、跳表兩個目標、三個空列探測位址與列步長一致；用 RISC-V 反組譯核對分支、參數與寫入順序。這辨認出一條填列路徑，不證它是唯一寫入者、複製服務成功或任何實際連線身分。
