# 另兩處查表鍵寫入：來源是依連線選出的 RAM 記錄

結論：`0x11b54` 和 `0x11c86` 與探索回呼的目的地相同，都是 `0x2000bfcc`；但兩者並非直接從當前 GAP 探索訊息取位址。它們共用另一段 APP 程式，先依訊息的連線 handle 選 RAM 記錄，再取記錄中的 bytes。不能據此斷定這批 bytes 從未來自探索，也不能斷定它們就是上一次探索事件的位址。

- `0x119c8` 的訊息分支從服務取得非空指標後，檢查首 byte；`0x11a08` 讀 +2 半字，比對三個保存的 handle，匹配才選索引 0、1 或 2。`0x1244e` 讀 +4 的 method，在通知或指示分支到 `0x11a40`。這裡的 +2 是半字，不是 `0x11544` 所讀的單 byte opcode。
- `0x11a14/18` 算出基址 `0x2000bfec`；`0x11a40..56` 令 s2 指向 `base + 12*index + 4`。三個起點是 `0x2000bff0 / 0x2000bffc / 0x2000c008`。兩個寫入點的高三個鍵位元組都來自這一列。第一處的低 byte 依賴收到的值；第二處的低 byte 也來自同一列。這是正常返回且相關保存暫存器未被破壞時的靜態資料流。
- 另見 `0x11986..0x1199e`：另一條路徑可請求對相同列內的六個 bytes 填零。呼叫本身不是成功清零或實際執行的證明，卻說明不能把 RAM 當成不可變位址常數。

驗證：原 BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`；從 AUIPC/ADDI 及兩對 AUIPC/SW 重新解出基址與目的地。另以參考 `wchble_rom.h` 做 RV32 freestanding C11 靜態斷言：`GATT_MSG_EVENT=176`、`ATT_HANDLE_VALUE_NOTI/IND=27/29`，`gattMsgEvent_t` 的 connHandle/method/msg 偏移為 2/4/8，通知與指示的 len/pValue 偏移皆為 2/4。這是參考型別布局與 APP 讀取位置的一致性檢查，未連裝置。
