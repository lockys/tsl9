# opcode 5：保存回呼、接收訊息、呼叫 APP 是三個不同步驟

範圍：WCH V1.31 參考 carrier（SHA-256 `133d37055626caa1ac0f0abd0b8ec4d8c5786a61d52e6a2ef24ae2705aa15a22`），壓縮載入按 Xwchc 解讀，不代表設備實際安裝版本。

1. **保存表指標。** `[0x401b0] = 0x6ad8e`。輸入表 a2 非零且前段正常返回、保存值不變時，`0x6adac` 寫 `[0x20002fb4] = a2`。這條 store 沒有呼叫表內函式。
2. **接收並分流。** 處理器 `0x6abc6` 的任務遮罩含 `0x8000` 時，`0x6abe2` 讀 `[0x20002fb0]` 的任務 ID，呼叫 `0x2000028c`；`0x6abee` 將返回的訊息指標 M 留在 s0。M 非空、M[0]=208 且 M[2]=5 時，到 `0x6ad50`。
3. **先看連線狀態，再決定是否前處理。** M[1] 非零直接到 `0x6aca6`；等於零時 `0x6ad5e` 先呼叫 `0x6c194(M[3], M+4, LE16(M+10), 8)`。第二參數是位址欄位的指標，不是其首 byte。正常返回後直接跳到相同位置，沒有測試 helper 返回值。此處不是 opcode 6/12 使用的 `0x6c964`。
4. **重新取表，才可能呼叫 APP。** `0x6acaa` 從 `0x20002fb4` 新讀表指標，再從表 +4 取函式指標，任一為零都略過。兩者非零時 `0x6acb4..b6` 以 s0 作 a0 間接呼叫。若仍為原 APP 表 `0x1a674`，且 s0 保持，目標是 `0x11544(M)`。非零狀態也可被派給 APP；是否填連線列由 APP 再檢查狀態，不是由 resident 的回呼門檻決定。

驗證：從 carrier 重算接收目標、啟動 slot 與 helper JAL，並解碼五個 Xwchc 載入的寬度、基底、目的暫存器及位移（0、2、1、10、3）。原 APP 對照見 `v4160-link-event-row-source.zh-TW.md`。未證 helper 不改訊息或表、訊息何時入隊、或首次實機事件時間。
