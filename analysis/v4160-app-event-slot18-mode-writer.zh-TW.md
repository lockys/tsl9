# v4.1.60：分派模式的清零與直接寫入

接續[模式讀取來源](v4160-app-event-slot18-mode.zh-TW.md)，只分析原 APP 映像的初始化與一處已確認的寫入，不推論其執行時序。

- Reset `0x186ee` 以 word 清零 `[0x20004080,0x2000c958)`。模式 byte `0x2000bfb5` 落在清零 word `0x2000bfb4` 的第二個 byte；零起算第 8141 筆、總計 8758 筆。若該迴圈正常執行且未受干擾，該 byte 在這次 store 後為零。
- `0x1074c` 的入口於 `0x10752` 把 `a0` 存至 `s0`。經過數個呼叫後，`0x10766` 取當時 `s0` 的低 8 位，`0x10776` 將它寫到 `0x2000bfb5`。前一處 `0x1076e` 寫零的是鄰近但不同的 byte `0x2000bfb4`。要把所寫值追溯到入口 `a0`，仍須確認中間呼叫返回並保存 `s0`。

離線 Python `-O` 核對原 APP SHA-256、三個原始指令窗、兩個 byte store 位址，並枚舉 8758 筆 reset word 確認覆蓋位置。這不是全域寫入者清單，也不證明何時會寫入模式 1。下一步追查 `0x1074c` 的已知呼叫者及其參數來源。未連接設備或修改原 BIN／正式來源。
