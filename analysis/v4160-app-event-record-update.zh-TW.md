# v4.1.60：APP 事件記錄的後續更新

接續[初始化與預設值](v4160-app-event-record-load.zh-TW.md)。本輪從固定 SHA-256 的原 APP BIN 核對一個非初始化更新點，著重 RAM 資料流，不推論外部輸入可達性。

`0x14be4..0x14bf4` 從 `[gp+104]` **重讀目前的 RAM 目的指標**，透過 `[0x4004c]` 傳入該指標、前序區塊建立的來源指標，以及 `256`。若仍使用 reset 初值，目的即 `0x2000c694`；若間接提供者遵循候選 byte-copy 語意並正常完成，這條路徑會整塊更新記錄資料，而非只更新預設記錄的第七個位元組。`0x14bf6` 隨後直接呼叫 `0x13052`。後者用固定 `0x2000c694` 當來源，不重讀 `[gp+104]`，所以只有兩者相等時，才能把更新目的與後續保存來源視為同一區域。未證明實際保存成功。

以 Python `-O` 比對原 BIN SHA-256 `0ee64183daaa140acac7dbb6c0f7c26d1fe625344ed158151731a9b2632fb667`、六個原指令窗及四個控制目標；另用 36 組合成向量檢查 256-byte copy 下各完整七 byte 視窗的第七 byte 偏移。這只驗證算術與局部資料流，不是硬體、完整記錄容量、呼叫約定或所有寫入者的證據。

下一步檢查其他 `[gp+104]` 引用是消費者、指標傳遞，還是第二個更新點，再把已驗證的 APP 路徑與依賴 resident 的部分分開。原 BIN 與正式來源不變。
