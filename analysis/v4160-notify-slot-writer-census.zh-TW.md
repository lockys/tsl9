# 通知表指標槽：哪些直接寫入形式已排除？

[執行時更新](v4160-notify-table-replacements.zh-TW.md)透過即時指標寫表，但儲存包裝從固定 RAM 讀取。本次只查指標槽本身。以 reset 的 gp=0x20004000 計，三個 word 合併為半開區間 `[0x20004060,0x2000406c)`。在 reset 複製迴圈 `0x186d2`，a1 由 gp 起每次加 4；索引 24、25、26 分別初始化三槽。這是已知寫入，**不屬於**下述直接定址樣式。

原 APP 全部 38,399 個半字對齊的四 byte 視窗中，以下兩種標準 RV32 寫入編碼對該 12-byte 區間均為 **0 命中**：以 gp 為基址的 `sb/sh/sw`；緊接 `lui/auipc` 並以其非零目的暫存器為基址的 32-bit `sb/sh/sw`（掃描器對 gp 一律採 reset 值）。比較含部分重疊。非零目的的 `addi rd,gp,96/100/104` 命中 12 處；形成槽位址不是寫入。例如 `0x1778a→0x1778e` 讀第三槽作七 byte 複製來源基址，`0x17a00→0x17a04` 讀第二槽後查表內 byte。這不證明該暫存器整個生命期唯讀。

`python analysis/check_v4160_notify_slot_stores.py <decoded-bin>`：固定映像 SHA，含三種寬度的 66 個邊界對照及兩種高位址指令的暫存器配對正反例；一般及 `-O` 結果一致。視窗也涵蓋資料，並非可達指令清單。**不能**據此排除複製迴圈、壓縮指令、經多條指令算出的別名、間接服務或非同步寫入。結論仍是條件式：保留 reset 綁定時兩者指向同一 RAM 頁；尚未發現初始化後改寫三槽的直接證據，也未證永遠同址。
