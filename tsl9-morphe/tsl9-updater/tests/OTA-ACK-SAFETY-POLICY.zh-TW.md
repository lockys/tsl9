# OTA ACK 風險與修復准入政策（離線評估）

結論：**目前沒有足夠證據把自動重試或重連宣稱為安全修復**。不修改產品語義；在回覆來源或效果不確定時，保守候選是停止 OTA、不再發 W／E，標示裝置狀態未知，要求依經驗證的恢復程序處理。停止亦不能撤銷已發出的擦寫或保證裝置可恢復。

## 依據及其界限

- 實際 `OtaSession.java` 的 `transmit()` 每次遞增 `sequence`；closure 僅用 token 篩掉舊的本地 written callback。`onPacket()` 沒有收到該 token，只按 active、state 和 command 篩選，傳輸中緩存首個早到回覆。W 接受單 byte `00` 或完整目前頁，空 W 會觸發 retry；ACK timeout 亦會 retry，最多 9 次。參見 [同連線排程](OTA-BLE-GENERATION.zh-TW.md)。
- [跨輪實驗](OTA-LATE-ACK.zh-TW.md)及同連線實驗用真實 session/codec 和合成封包展示：無頁識別的 `00` 可使錯誤頁前進；完整不同頁 echo 可拒絕，但同頁跨嘗試或跨輪 echo 仍不可區分。它們不是 Android GATT 或設備觀測。
- [ID2580 BOOT 靜態分析](../../../analysis/boot2580-ota-page-conflicts/README.md)在特定前提下顯示比對成功後請求**空** W 回覆，並非 BLE 實際送達證據，亦未證與目標 ID2966 配對。不能把合成 `00`、echo 或空回覆假定為目標實際格式。若空 ACK 可作成功，則不同頁、不同嘗試的空 ACK 在封包內容上完全相同；host token、等待時間或單獨增加 callback token 均不能辨識其來源。現行程式並不接受空 W 成功。
- `BleClient.close()` 的 decoder 清理及不同 GATT 身分過濾對跨連線舊 callback 有幫助，但同連線重試與設備端殘留回覆不因此獲得識別；詳見 [BLE 分析](OTA-BLE-GENERATION.zh-TW.md)。尚未證明實際平台／設備會產生或遞送上述遲到封包。

## 候選策略及安全條件

| 策略 | 可保證／限制 | 准入條件 |
|---|---|---|
| 原連線重試 W | 本地 callback token 可隔離舊 closure；不能隔離未標識的舊 ACK，重試可能造成多份回覆。 | 只有協定提供並核驗每次請求唯一識別（含 session 和 attempt），或有可驗證的排空及精確一次語義，才能以 ACK 推進。頁 echo 單獨不足。 |
| timeout 後重連並重啟 | 新 GATT 隔離部分 host 端舊事件；不能單憑重連證明設備無殘留回覆、已寫入狀態或重送冪等。 | 先證明端到端隔離、設備重新同步、BOOT/UID 及映像相容性，並證明從頭重送及斷電恢復安全；否則不自動重啟。|
| 不確定即停止 | 不再因模糊 ACK 推進或自動重送；犧牲可用性，不能修復已部分寫入的設備。 | 必須驗證所有 timeout、無效／模糊 ACK、斷線及取消路徑停止後不送下一頁或 E，且不宣稱成功。這是候選政策，不是現行產品保證。|
| 協定升級 | 設備在 ACK 中回傳不可混淆的 session nonce、page、attempt，主機嚴格匹配，重複及過期回覆拒絕。 | 需要兩端協定與設備支援、nonce 不重用和明確重試／重開語義；還需獨立驗證實際寫入與完整性。只在主機產生 token 無效。|

即使沒有 timeout，若協定或傳輸可能重複遞送前一頁的無識別 ACK，下一頁仍有歧義；停止僅在能偵測到不確定時有效，不能神奇辨識看似正常的重複 ACK。若無來源識別或已證明的無重複、順序及隔離保證，不能證明逐頁進度安全。readback 若存在也需要驗證其完整性與回覆關聯，不能僅靠 E 回覆宣稱持久化或可開機。

## 可驗證修復計畫

1. 保存可追溯的目標設備及 BOOT 版本、協定規格或封包證據，釐清 W 回覆長度、空回覆意義、重複及排序；不要將其他 BOOT 的靜態推論當成目標事實。硬體操作須另行授權和安全設計。
2. 純 JVM 使用虛擬時鐘及合成 transport 驗證候選停止模型：正常成功、ACK timeout、callback 前後遲到 ACK、重複 ACK、取消／斷線後回覆、空與錯頁及同頁回覆；斷言停止後無 W/E、不成功。另設不安全重試及未隔離重連負例，證明相同空 ACK 不能被 token 區分；不得把模型結果當產品測試。
3. 對實際 Android transport 以替身測試 close、不同 GATT 舊 callback/partial frame、同 GATT 重複通知和 callback 排程；證明邊界而非假設平台順序。具體排程見 [BLE 分析](OTA-BLE-GENERATION.zh-TW.md)。
4. 在任何產品變更前，明確定義不確定狀態、UI、取消、恢復及完整性驗證，測試錯誤路徑及相容性；若缺少必要的協定或恢復證據，維持停止／人工處理而非宣稱安全自動恢復。
